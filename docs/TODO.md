## Full bug audit + housekeeping pass (2026-08-05)

Right after finishing Tier 1, ran a full audit of every `js/` file (not just this session's changes) plus a cleanup/OOP-conformance pass and a diagrams-sync check, using parallel forked agents to cover the whole codebase, then personally verified each finding against the real code (and live behavior where practical) before fixing anything — none of this was taken on trust. Five real bugs and two real cleanup gaps found; every fix below is applied and verified.

- [x] **`tripsApi.js` `saveTrip()` crash on expired/failed session** — `user.id` was read with no null check on `user`; an expired access token + failed silent refresh (plausible on a longer drive through spotty connectivity) resolves `getUser()`'s `user` to `null` instead of erroring, and nothing in the call chain caught the resulting throw. Left the trip button permanently disabled and the summary frozen on "Saving…" until a reload. Fixed with an explicit `if (!user) return new Error(...)`, fitting the function's existing return-an-error-or-null contract with no other changes needed.
- [x] **`auth.js`'s `onAuthStateChange` reset the live display on every token refresh, not just real sign-ins** — Supabase fires this listener for `TOKEN_REFRESHED` (automatic, roughly hourly) with a valid session, same as `SIGNED_IN`; the old `session ? showApp() : showAuth()` reacted to both identically, and `showApp()` unconditionally calls `startApp()`, which flashes the live zone/speed display to blank and resets the zone-change hysteresis tracker to a cold start — silently skipping the zone-change chime/flash/haptic cue for whatever transition happened to land on a refresh. Reproducible on any trip long enough to span one refresh, i.e. an ordinary drive. Fixed by only calling `showApp()` on `event === "SIGNED_IN" || event === "INITIAL_SESSION"`; `!session` still always shows the auth screen regardless of event type. Verified the exact Supabase v2 event name set against current docs before writing this, rather than guessing (getting a listener like this wrong risks breaking sign-in entirely).
- [x] **`VehiclePicker` cross-account vehicle leak on a shared device** — `localStorage["paceometer-vehicle"]` is per-origin, not per-account, and the app never reloads the page between sign-out/sign-in (screen visibility just toggles); a second person signing in after a first person signed out silently inherited the first person's selected vehicle, with their trip then saving to Supabase (`vehicle_label`/`gallons_used`/`gallons_saved_by_speeding`) computed against the wrong car's MPG. Fixed by making `VehiclePicker`'s existing `_clear()` (previously only wired to the Clear button) public as `clear()` and calling it from `app.js`'s `stopApp()` — the same session-ending cleanup point `trip.cancel()` already uses. Verified live: set a fake vehicle in `localStorage`, signed out, confirmed it read back `null`.
- [x] **`dashboardView.js`'s `setPace()` hand-rolled a duplicate of `paceSecondsFor()`** — same `t = d/v` formula this project treats as literature-validated (Peer & Gamliel 2013) and explicitly documents as needing to stay traceable to one place, copy-pasted instead of calling the already-imported-elsewhere function. A future formula change wouldn't have propagated here, and nothing would have caught the two silently disagreeing. Fixed by calling `paceSecondsFor()` directly; the now-unused `PACE_MIN_SPEED_MPH` import was removed too. Verified live via a simulated drive: 112mph → "5:21 / 10mi", matching `10/112×3600 ≈ 321s` exactly.
- [x] **`dashboardView.js`'s `showTripSummary()` used `innerHTML`, contradicting the documented "no XSS sinks" claim** — not currently exploitable (the interpolated value is always a `formatDuration()`-formatted number string), but `docs/TODO.md`'s own 2026-07-16 security-audit entry states "textContent only, no innerHTML anywhere," and that was quietly false the moment this line existed — a future edit interpolating a less-trusted string into the same call would silently inherit an XSS-capable sink nobody would think to re-audit. Fixed with `createElement`/`textContent`/`append` instead. Verified the resulting DOM is byte-identical to the old `innerHTML` output (`<span class="trip-summary-value-prefix">only</span> 2:05`) via direct inspection, and confirmed it still renders correctly.
