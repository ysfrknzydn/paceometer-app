# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Paceometer: a real-time in-car pace/speed display, built as an installable Progressive Web App. Part of a GWU research project testing whether a pace display (not just a speedometer) reduces speeding. The literature review, research plan, and design justifications live in a **sibling repo**, `/Users/yusuf/paceometer_lit_review` (GitHub `ysfrknzydn/paceometer`) — check `lit_review.md` and `paceometer_review.qmd` there before adding or changing any behavior-design decision (pace formula, display layout, zone thresholds), rather than inventing a rationale. Not every phrase in that repo's `research_plan.qmd` is literature-backed — some (e.g. "optimal zone") are this project's own unresolved design extensions, not cited findings; don't assume plan language implies a citation exists.

## Commands

There is no build step, no bundler, no package.json, and no linter for the **shipped app itself**: this is intentional (zero-budget, plain HTML/CSS/JS). There is a test suite (see below) and, as of 2026-08-03, CI (`.github/workflows/tests.yml`, runs on every push/PR). Neither gates the GitHub Pages deploy itself, which is still just "push to `main`." `tests/e2e/` (2026-08-06) is the one exception with its own `package.json` — dev-only tooling, scoped to that directory, same precedent as `python/`'s own separate `requirements.txt`; it doesn't touch the app's zero-dependency runtime.

- **Run locally**: `python3 -m http.server 8000`, then open `http://localhost:8000`. Must be served over HTTP(S) — opening `index.html` directly as a `file://` URL breaks the ES module imports. Geolocation works on `localhost` without HTTPS, but testing from a phone requires the deployed HTTPS URL (a phone hitting your laptop's LAN IP is not a secure context, so geolocation is blocked there).
- **Deploy**: push to `main`. GitHub Pages serves directly from the repo root on that branch — no CI/build step in between. Live at `https://ysfrknzydn.github.io/paceometer-app/`.
- **Sanity-check JS**: after editing any `js/*.js` file, at least syntax-check it. These are ES modules, so a plain `node --check app.js` fails on `import`/`export` — either copy to a `.mjs` file first (e.g. into the scratch dir) and `node --check that.mjs`, or simpler, pipe it through stdin with an explicit module type: `node --input-type=module --check < js/app.js` (no copy needed, works in place).
- **Unit tests (2026-07-31)**: `js/math/` holds the app's pure pace/zone/geo/parsing/fuel formulas (no DOM, no browser APIs) and has real tests -- run with `node --test js/math/*.test.js` (Node's built-in test runner, zero added dependency). A parallel, independently-written Python port lives in `python/paceometer_math/` (dev-only -- never runs in the shipped app, no Pyodide) with its own pytest suite (`cd python && ./.venv/bin/pytest`, or `pip install -r python/requirements.txt` into your own venv first). CI installs from `python/requirements.lock.txt` instead (`pip install --require-hashes -r python/requirements.lock.txt`, 2026-08-19 security audit finding) — a `pip-compile --generate-hashes` output covering every transitive dependency, not just the two direct ones, so a compromised release published under an already-pinned version number can't install silently. Regenerate it after changing `requirements.txt`: `pip install pip-tools && pip-compile --generate-hashes --output-file=python/requirements.lock.txt python/requirements.txt`. Local dev can keep using the plain `requirements.txt` install above — the hash check is CI's job, not a local-iteration requirement. Both suites check themselves against the same fixtures in `tests/golden_vectors/` (`pace_zone.json`, `fuel_math.json`), so a bug in one language's formula shows up as a disagreement with the other -- regenerate a vectors file with the script pattern in git history (import the real `js/math/*.js` functions, run them over representative inputs including the documented boundary cases, write the JSON) if you change a formula. `python/tests/` also covers `python/fuel_pipeline/`'s pure cleaning/filtering logic (`clean.py`). `fetch.py`/`publish.py` do real network I/O and are deliberately not unit tested, the same distinction as GPS/DOM/network below. **`js/trip/trip.test.js` (2026-08-19, council review Tier 7)**: `Trip` is stateful and touches `localStorage` (unlike everything else in `js/math/`), but its accumulator math itself (`recordSample`/`finish`'s distance/pace/zone/speed-limit/fuel derivations) is exercised the same way — run with `node --test js/trip/*.test.js`, no golden-vector/Python mirror since this isn't a pure-function module. Tests construct `Trip` with `{ checkpointing: false }` for pure-math cases (no `localStorage` involved at all) and a minimal in-memory `localStorage` polyfill (assigned to `globalThis.localStorage` at the top of the file, since Node has no browser Web Storage global by default) for the handful of checkpoint-shape tests — those are deliberately narrower than `tests/e2e/specs/tripCheckpoint.spec.js`'s real-browser end-to-end coverage, just confirming the write/read/clear/staleness contract in isolation. One test directly encodes the historical `timeSavedBySpeedingSeconds` sign-flip bug (2026-07-26 — see that entry below) as a regression case: a driver going 60mph against a 50mph limit must show a *positive* saved-time figure, not the old always-`0` result. Everything outside `js/math/` and `js/trip/trip.js`'s accumulator logic (GPS, DOM, network, Supabase) is still untested beyond syntax-checking and manual/Playwright verification; see the module structure note under Architecture for why those pieces can't be unit-tested the same way. CI (`.github/workflows/tests.yml`) runs all three JS/Python suites on every push/PR.

- **Database schema changes**: use versioned migrations via the Supabase CLI (`brew install supabase/tap/supabase`), not the old single-file `supabase/schema.sql` (deprecated, kept only for history). Workflow: `supabase migration new <description>` creates a timestamped file in `supabase/migrations/`; write the SQL there (additive changes as idempotent `alter table ... add column if not exists`, same reasoning as before — the live table already exists and won't be recreated); then `supabase db push` applies any pending migrations to the linked remote project. The CLI must be linked once per machine (`supabase login --token ...`, then `supabase link --project-ref ojhhlxmbawckknnpgmfj`) — see git history around 2026-07-14 for how that was set up if it needs redoing. `supabase db push` needs the database password (Supabase dashboard → Connect → Direct → password, or reset it there) passed via `-p`; it does NOT need Docker. (`supabase db pull`/`db dump` do need Docker for the shadow-database/pg_dump-version-matching machinery — avoid those; if you ever need a raw schema dump instead, `brew install postgresql@17` and use `pg_dump` directly against the session pooler host, since the direct-connection hostname is IPv6-only and this network doesn't resolve it.) Migration history is tracked in a remote table the CLI manages — `supabase migration list -p <password>` shows what's applied. Never type a Supabase access token or DB password directly into a shell command visible in a Claude Code session transcript (`! command`); write it to a local file outside the repo first (outside the `!` proxy, in a real terminal window) and read it via command substitution instead, e.g. `-p "$(cat ~/.some_token_file)"`.

Secrets (e.g. `GROQ_API_KEY`) are set with `supabase secrets set GROQ_API_KEY=<value>` — same "never type the raw value into a visible shell command" rule as the DB password; source it from Keychain (`security find-generic-password ...`, see the credential-storage standing instruction) or a local file outside the repo, never inline. `supabase functions deploy` does not need Docker; local *serving* (`supabase functions serve`, for interactively testing against the full local stack) does. A function can also be smoke-tested without Docker at all by running it directly — `deno run --allow-net --allow-env supabase/functions/<name>/index.ts` — and hitting it with `curl`, which is how `transcribe-feedback` was verified before any deploy.

## Architecture

**No framework, no bundler.** `index.html` loads a single entry point, `js/auth.js`, via `<script type="module">`; everything else is pulled in through ES module imports (including the Supabase client from `esm.sh`, a CDN that serves npm packages as ES modules — used instead of a local `node_modules` install since there's no build step).

**Module structure (2026-07-31 restructuring)**: `js/app.js` was originally one ~1360-line file holding every concern (GPS, speed-limit lookup, zone/pace math, trip recording, DOM rendering, audio/haptics, settings, the dev-only simulated-drive tool) as module-scope functions and shared `let`s. It's now split into one class/module per concern, each owning the state it used to share implicitly, with `js/app.js` reduced to a composition root that instantiates and wires them together:
- `js/math/` — pure functions and constants only (`paceMath.js`, `zoneState.js`, `geoMath.js`, `speedLimitParsing.js`, plus `fuelMath.js` and `unitsMath.js` added later, 2026-08-03/08-07 — see their own dated Architecture entries below). No DOM, no `fetch`, no `localStorage`. `paceMath.js`/`zoneState.js`/`geoMath.js`/`speedLimitParsing.js`/`fuelMath.js` are the set mirrored in `python/paceometer_math/` for testing (see Commands above) — `unitsMath.js` deliberately isn't, see its own header for why. If you're looking for `nextZoneState`, `marginalSecondsSaved`, `zoneCeilingMph`, `haversineMeters`, `parseMaxspeedTag`, etc., they live here now, not in `app.js`.
- `js/gps/geolocationTracker.js` — `GeolocationTracker` class: `watchPosition`/`clearWatch`, the Screen Wake Lock trio, and `deriveSpeedMph()` (the `coords.speed`-or-Haversine-fallback logic, shared by real GPS and the simulated-drive tool).
- `js/speedLimit/speedLimitService.js` — `SpeedLimitService` class: the Overpass lookup/mirrors/retry/cache/throttling, plus the dev-override hook the simulated-drive tool uses.
- `js/trip/trip.js` + `tripsApi.js` — `Trip` class (start/recordSample/finish, all the accumulator fields) and the isolated Supabase write.
- `js/ui/dashboardView.js` + `settingsControls.js` — `DashboardView` class (every DOM ref and DOM-writing function) and `SegmentedSetting`, one reusable class replacing what used to be three near-identical Appearance/Zone-Sensitivity/Sound blocks.
- `js/feedback/audioFeedback.js` — `AudioFeedback` class: the Web Audio tones and haptic patterns.
- `js/dev/simulatedDrive.js` — the entire dev-only simulated-drive tool, deliberately self-contained (owns its own DOM refs) — see the Pre-launch checklist below, now just "delete this file + its one import line in `app.js` + its HTML block."

This was a structural-only refactor — every formula, threshold, and piece of wording below is unchanged; only *where* the code lives moved. The historical narrative below still cites `js/app.js` by habit in places (e.g. "`setZoneDisplay` in `js/app.js`") for pieces that have since moved into one of the modules above — if a cited function name isn't in `app.js` anymore, check the module map first before assuming it was removed.

**Module graph**: `auth.js` (entry) → imports `supabaseClient.js` (client init) and `app.js` (the composition root, still exports exactly `startApp`/`stopApp`/`setViewportZoomEnabled` — `auth.js` itself needed zero *structural* changes for the 2026-07-31 restructuring, though it wasn't converted to a class until 2026-08-05, see below). `app.js` in turn imports every module listed above.

**Architecture diagrams** (`docs/diagrams/`, added 2026-07-31): a package/dependency diagram, a class diagram, a sequence diagram (one GPS fix flowing through the modules above), and an activity diagram for `nextZoneState`'s own branching logic — all real UML via PlantUML (`.puml` sources checked in alongside the rendered `.pdf`s), not the mermaid approximation. Regenerating after an edit needs `brew install plantuml graphviz` (Graphviz gives PlantUML's layout engine much cleaner output than its built-in one), then `plantuml -tpdf <name>.puml` from that directory.

**Screen-gating pattern**: `index.html` has five top-level `.screen` divs — `#auth-screen`, `#onboarding-screen` (added 2026-08-07, see the Onboarding entry below), `#app`, `#settings-screen` (added 2026-07-16), and `#trips-screen` (added 2026-08-07, see the Trip history entry below) — toggled via the `.hidden` class. `js/auth.js`'s `AuthController` class (converted from loose module-scope code 2026-08-05, see below) owns the `supabase.auth.onAuthStateChange` listener, the single source of truth for the *signed-in vs. signed-out* split — it calls `startApp()` (begins `watchPosition`) and shows either `#onboarding-screen` (a genuine fresh `SIGNED_IN`) or `#app` (`INITIAL_SESSION`, a restored session) depending on which event fired, and calls `stopApp()` (clears the GPS watch, resets trip state) and shows `#auth-screen` when no session exists; `_showApp()`, `_showAuth()`, and `_showOnboarding()` all force every *other* one of these five screens hidden, so none can stay visible across a transition it doesn't belong in. Don't add a second place that shows/hides `#auth-screen`/`#app`/`#onboarding-screen`; route all auth-driven visibility changes through that listener. The `#app` ↔ `#settings-screen` and `#app` ↔ `#trips-screen` toggles are each intentionally a *separate*, independent mechanism (`settings-nav`/`settings-back` and `trips-nav`/`trips-back` listeners, both in `DashboardView`'s constructor, not `app.js`) — the driver stays signed in the whole time, so neither belongs in the auth listener, same reasoning as the trip-summary inline swap below. `#onboarding-screen`'s own two exits (`onboarding-settings-btn`/`onboarding-skip-btn`) are the one exception, wired directly in `AuthController` rather than `DashboardView` — onboarding is conceptually part of the auth flow (a one-time detour between signing in and reaching the dashboard), not a driver-initiated navigation the way Settings/Trips are mid-session, so it stays with the class that already owns every other auth-adjacent screen transition.

**`AuthController` class (2026-08-05)**: `js/auth.js` was the one module never converted to a class in the 2026-07-31 restructuring (see above) — it held real state (`mode`, sign-in vs. sign-up) and behavior as loose module-scope code and top-level functions, the single OOP-convention gap in the codebase, found and fixed in a full-codebase audit. Converted to `AuthController`, same constructor-refs-then-methods shape as `DashboardView`; no external contract changed, since nothing imports from `auth.js` (it's the entry point, loaded directly by `index.html`). Two real bugs came out of the same change: (1) the `onAuthStateChange` listener used to react identically to *any* event carrying a session, including `TOKEN_REFRESHED` (automatic, roughly hourly) — since `_showApp()`/`showApp()` unconditionally calls `startApp()`, which resets the live zone-display and the zone-change hysteresis tracker to a cold start, this silently flashed the live display and skipped the zone-change chime/flash/haptic cue on whatever transition happened to land on a token refresh, reproducible on any ordinary drive longer than one refresh interval. Fixed by only calling `_showApp()` on `event === "SIGNED_IN" || event === "INITIAL_SESSION"`; `!session` still always shows the auth screen regardless of event type, since a missing session is the one signal that unambiguously means "not authenticated." (2) `_showAuth()` didn't reset `mode` back to `"sign-in"`, so signing out mid-"sign up" left the button reading "Sign up" on the next view of the auth screen — fixed by calling `_setMode("sign-in")` there too.

**Password reset flow (2026-08-06)**: raised in live testing — there was no self-serve recovery, so a friend who forgot their password was stuck until a manual dashboard reset, which doesn't scale. Three pieces, all in `AuthController`: (1) a "Forgot password?" link (`#auth-forgot-password`) switches `_mode` to a new `"reset-request"` state — the existing `#auth-form` is reused with the password field hidden, `resetPasswordForEmail(email, { redirectTo: <deployed origin> })` on submit; (2) the emailed link brings the driver back to the deployed site with a `PASSWORD_RECOVERY` session, which `onAuthStateChange` checks for *before* the existing `!session`/`SIGNED_IN` branches (both checked first would never see it, since a recovery session isn't falsy) and routes to `_showAuth("reset-confirm")` rather than treating it as a real sign-in — `_showAuth()` now takes a `mode` param specifically so this also works correctly if the link is opened in a tab that already had the live app open; (3) `"reset-confirm"` mode shows a separate `#reset-confirm-form` (just a new-password field) that calls `updateUser({ password })`, and a successful call goes straight into the app via `_showApp()`, since completing a recovery is itself a real, completed sign-in. Email delivery against the deployed GitHub Pages URL needed a Supabase dashboard fix (Site URL/Redirect URLs previously pointed at a `localhost` default) — done by the user in the dashboard, confirmed via a real end-to-end test the same day (requested a reset on the deployed site, received the email, clicked through to the deployed URL's set-new-password screen, set a password, signed in).

**Real bug found closing that out, worth remembering for any future testing that involves an actual sent email**: the standing test account (`paceometer-test@example.com`, see memory) can never be used to test anything that sends a real email — confirmed via a direct `POST {SUPABASE_URL}/auth/v1/recover` call that Supabase's own GoTrue server hard-rejects the `@example.com` domain (`error_code: "email_address_invalid"`) as a known non-deliverable RFC 2606 reserved domain, while an arbitrary `@gmail.com` address on the exact same endpoint succeeds normally. This has nothing to do with this project's config — it's Supabase's own built-in validation, unconditional. Signing in with that account still works fine (`signInWithPassword` doesn't send anything, so it never hits this check) — only email-sending flows (`resetPasswordForEmail`, and presumably signup confirmation emails if this account were ever used fresh) are affected. If a future feature needs to verify a real sent email, it needs a real deliverable address, not the standing test account.

**Two real bugs found building the above, both would have shipped invisibly without live testing**: (1) `_setMode()` unconditionally clears `#auth-error`'s text at the end of every call — the *pre-existing* sign-up flow set the "check your email to confirm your account" message and then immediately called `_setMode("sign-in")` right after, in the same synchronous tick with no paint in between, silently wiping the message before a signing-up driver could ever see it. Never caught before because nothing was watching for it — the message just looked like it "didn't show up sometimes." Fixed by reordering both the sign-up path and the new reset-request path to call `_setMode()` *first*, then set the message. (2) Hiding `#password-field` with CSS alone during `"reset-request"` mode wasn't enough: a `required`, empty, non-focusable field still silently blocks native form submission rather than being excluded from constraint validation — confirmed live (Chrome logs "An invalid form control … is not focusable" and the submit event never fires at all, not even to reach `_handleSubmit()`). `display: none` on an ancestor is *not* one of the spec's documented reasons a field is barred from constraint validation; only the field's own `disabled` property is guaranteed to do that. Fixed by toggling `this._passwordInput.disabled` alongside the `.hidden` class in `_setMode()`.

**Sign-in/sign-up tab split (2026-08-06)**: raised in live testing — the previous `#auth-toggle` (a small text link below the submit button, "Need an account? Sign up") was subtle enough that testers genuinely couldn't tell which mode they were in, causing real sign-in errors. Replaced with `#auth-mode-switch`, a real two-option tab reusing the existing `.segmented-control`/`.segmented-option` CSS from Settings' Appearance/Zone Sensitivity controls, so it reads consistently with the rest of the app rather than introducing a new visual language. Wired directly in `AuthController` (two click listeners calling `_setMode(btn.dataset.authMode)`) rather than through `SegmentedSetting` — that class is deliberately localStorage-backed (see its own header comment) for real persisted preferences; which auth mode you're on is momentary UI state, not something worth remembering across visits.

**`PasswordToggle` class (2026-08-06)**: also raised in live testing — testers hit typos with no way to confirm what they'd actually typed before submitting. `js/ui/passwordToggle.js`'s `PasswordToggle` is a small reusable eye-icon show/hide control, same "one instance per control" shape as `SegmentedSetting` — constructor takes an input element and a button element, no shared state between instances. `AuthController` owns two: one for `#password` (sign-in/sign-up), one for `#new-password` (the password-reset "set new password" field, see above). Toggling flips the input's `type` between `password`/`text` and updates the button's `aria-pressed`/`aria-label`; the eye ↔ slashed-eye icon swap is pure CSS (`.password-toggle[aria-pressed="true"] .password-toggle-icon-eye { display: none }` and its inverse) — no JS icon-swapping logic, `aria-pressed="false"` (default) shows the plain eye ("click to reveal"), `true` shows the slashed one ("click to hide"), the same convention most password fields' own built-in reveal icon uses. **Real bug caught by looking at the actual screenshot, not visible from the CSS source**: the generic `.auth-form button, .trip-btn { ... }` rule (meant only for the primary submit button) has higher specificity (`.auth-form button` = one class + one type = 0,1,1) than a bare `.password-toggle` class alone (0,1,0), and was silently winning — the toggle button rendered with the primary button's full gradient/shadow/padding instead of a plain inline icon. Fixed with a `.auth-form .password-toggle` selector (0,2,0), which unambiguously outranks it regardless of source order.

**Sign-up comfort screen (2026-08-06)**: raised in live testing — a new driver had no plain-language answer to "why does this want my location" until after creating an account and finding Settings → Privacy, by which point they'd already had to trust the app blind. `#signup-explainer`, shown alongside `#auth-form` (not a separate route) whenever `_mode === "sign-up"`, same toggle mechanism as everything else in `_setMode()`. Deliberately short — three sentences, not the full Settings → Privacy section — since this is a comfort/trust beat, not the actual legal artifact (Tier 4's Privacy Policy/ToS in `docs/TODO.md` is that). The copy itself was condensed from the already-reviewed Settings → About/Privacy text rather than drafted fresh, and went through the standing wording check (plain comprehension + "could this read as encouraging speeding?") with the user picking a "privacy-first" ordering (location handling, then what the app shows, then what's saved) out of two drafted candidates. Styled with the same `.trip-summary-cost`/`.vehicle-selected` "info card" visual language (rounded corners, `--accent-2-dim` tint) as the rest of the app's secondary-info cards, at the same 320px width as everything else on the auth screen.

**Screen wake lock (2026-07-27)**: real-drive testing surfaced that the phone would fall asleep mid-drive like any other web page, forcing the driver to keep tapping it awake — the opposite of an instrument meant to be glanced at. `requestWakeLock()`/`releaseWakeLock()` in `js/app.js` wrap the Screen Wake Lock API (`navigator.wakeLock.request("screen")`) and are called from `startApp()`/`stopApp()` — i.e. tied to the tracking session (signed-in + `#app` visible), the same lifecycle boundary `watchId` uses, not to which sub-screen (settings vs. live dashboard) is showing. The OS releases the lock automatically whenever the tab/PWA is backgrounded (app switch, real screen lock), so a `visibilitychange` listener re-requests it when the page becomes visible again while a watch is still active, or a brief backgrounding would otherwise lose the lock for the rest of the drive. Supported on iOS Safari 16.4+ and Chrome/Android, including standalone PWA mode; the request silently no-ops (falls back to the OS's normal timeout) on unsupported browsers or if the request itself fails (e.g. low battery on some platforms) — not yet verified against an actual drive, only smoke-tested that the app still loads.

**Wake lock actually didn't hold on a real drive (2026-08-11)** — the "not yet verified against an actual drive" caveat above turned out to be hiding two real bugs, found by real-world testing months after the feature shipped: the screen kept falling asleep despite this code existing. Both fixed in `js/gps/geolocationTracker.js` (`GeolocationTracker`, which now owns this logic — see the 2026-07-31 module restructuring above; `js/app.js`'s `startApp()`/`stopApp()` still just call `geoTracker.requestWakeLock()`/`releaseWakeLock()`, unchanged):

1. **No qualifying user gesture on the most common path.** `startApp()`'s call to `requestWakeLock()` has zero user gesture behind it for a *restored* session — `AuthController` reaching `INITIAL_SESSION` on reopening an already-installed PWA, the ordinary way a driver starts a drive, happens before any tap on the page at all — and is borderline even for a fresh sign-in, since it fires after an async Supabase round trip, well outside a click handler's own gesture window on strict engines. Safari/WebKit's Screen Wake Lock implementation is documented to require a real user gesture (Chrome's does not, which is exactly why this went unnoticed in this project's own Chromium-based Playwright testing — `document.visibilityState` and the wake-lock permission both need to be explicitly granted in a Playwright context, `screen-wake-lock` isn't implied by `geolocation`, and even then Chromium never enforced a gesture requirement to begin with, so no test in this suite could have caught a Safari-specific failure). Fixed the same way this project already worked around an identical class of gesture-gated-API restriction for `AudioFeedback`'s `AudioContext` (see that file) — a `pointerdown` listener that (re-)attempts `requestWakeLock()` on every real tap while `_watchId !== null` (i.e. only during an active tracking session), guarded by `this._wakeLock === null` so it's a no-op once a lock is genuinely held. This doesn't replace the `startApp()`-time attempt (still correct and sufficient on Chrome/Android) — it's the fallback that makes the first *and every subsequent* real tap on the driving screen (Start/End Trip, any nav icon) a chance to acquire or recover the lock on browsers that need a gesture.
2. **A stale, never-nulled `_wakeLock` reference could permanently block every future re-request.** The sentinel `navigator.wakeLock.request()` returns can be released by the browser at any time without the app calling `releaseWakeLock()` itself (tab backgrounded, real screen lock, low battery on some platforms) — and nothing was listening for that. `_wakeLock` stayed a reference to an already-dead sentinel, so the existing `visibilitychange`-triggered re-request (and the new `pointerdown` one above), both gated on `this._wakeLock === null`, would silently see a non-null value and skip re-requesting for the rest of the session — the first silent auto-release effectively disabled wake-lock recovery permanently, independent of the gesture issue above. Fixed by registering `this._wakeLock.addEventListener("release", () => { this._wakeLock = null; })` right after a successful request, so the tracked state always matches reality regardless of *why* the release happened.

Also stopped silently swallowing a failed request (`catch {}` → `catch (error) { console.warn(...) }`), since the original silent failure is exactly why this went undiagnosed for as long as it did — a future live-testing session can now see the real `DOMException` name via remote debugging (Safari Web Inspector / `chrome://inspect`) if it ever fails again.

**Verified**: both fixes confirmed live via a real Playwright Chromium session with the `screen-wake-lock` permission explicitly granted (not part of the checked-in suite — this permission isn't otherwise needed by any existing spec, and there's no way to simulate Safari's gesture restriction in Chromium to test fix #1 directly) — instrumented `navigator.wakeLock.request` to confirm: the lock acquires successfully on page load in this engine (as expected, Chrome never needed a gesture), and, after force-releasing the held sentinel to simulate a silent browser drop, the very next real tap correctly re-acquires it — proving both the `release` listener (fix #2) and the `pointerdown` fallback (fix #1's mechanism) work as intended. Fix #1's actual root-cause claim (Safari's gesture requirement) rests on documented WebKit behavior and the precedent of this exact codebase already needing the identical workaround for `AudioContext`, not a directly reproduced Safari failure — worth confirming against a real iPhone on the next live drive.

**Speed → pace pipeline** (`js/app.js`): `handlePosition` prefers `coords.speed` from the Geolocation API; when that's `null` (no GPS chip — true of every desktop browser, and occasionally a phone's first fix), it falls back to a Haversine distance/time delta between consecutive fixes. Either way, the *only* output that leaves `handlePosition` is a plain `mph` number — raw lat/lng from `lastPosition` is used transiently for the fallback calc and never stored or transmitted. Pace is computed live from that same `mph` value using `t = d/v` (Peer & Gamliel 2013, Formula 1: minutes to cover a fixed 10-mile reference distance) — this is the one formula in the codebase that's directly literature-validated; if you change the reference distance or the formula shape, that traceability is lost, so check the sibling lit-review repo first (see "What this is" above). `DashboardView.setPace()` calls `paceSecondsFor()` (`js/math/paceMath.js`) directly rather than recomputing this formula itself — it briefly hand-rolled a duplicate of the exact same calculation until a 2026-08-05 audit caught it, which would have silently diverged from `paceSecondsFor` on any future formula change with nothing to catch the disagreement.

**GPS fallback noise guards** (`js/gps/geolocationTracker.js`, `deriveSpeedMph()`; `MAX_FIX_ACCURACY_METERS`/`MAX_PLAUSIBLE_MPH` in `js/math/geoMath.js`): desktop Wi-Fi/IP-based positioning is coarse and jumps between fixes, so the Haversine fallback above can turn ordinary position noise into a large apparent speed. Two guards catch the extreme case: a fix isn't remembered as "last known position" for the delta calc unless its reported `coords.accuracy` is within 100m, and any resulting speed above 200mph is discarded outright rather than shown/recorded (2026-07-15, added after "huge numbers on refresh" during dev-server testing). **Closed 2026-08-05**: two fixes could still differ by tens of meters from ordinary noise even while both individually passed the 100m accuracy gate — e.g. a stationary laptop could show a spurious few-mph or double-digit reading. Fixed by only trusting a delta as real movement once the apparent displacement exceeds the *combined* accuracy radius of both fixes (`distance > (lastAccuracy ?? 0) + (currentAccuracy ?? 0)`), reporting `0` (genuinely stationary) rather than the noisy value otherwise — `??0` treats a missing accuracy (the simulated-drive tool's synthetic fixes) as zero tolerance, same lenient handling as the remember-last-position check just above it. Verified live on the local dev server: stable `0` over ~18s while genuinely stationary, no console errors. Much smaller-magnitude on a real phone (GPS accuracy ~5-10m vs. desktop's hundreds) so this was always a bigger practical risk on desktop/dev-server testing than on-device, but the fix isn't platform-conditional — it applies everywhere the fallback path runs.

**Core Function/Core Loop: the zone indicator** (`js/app.js`): the app's build follows a 5-stage MVP funnel from `research_plan.qmd` (`@sec-mvp-funnel`) — Core Function, Core Loop, Accessory Features, Surface Area Check, Retention Hook — each stage gating what gets built next. `marginalSecondsSaved(mph)` answers the Core Function question directly: at the current speed, would going `ZONE_SPEED_INCREMENT_MPH` (+10mph) faster still save `ZONE_THRESHOLD_SECONDS` or more over the `PACE_REFERENCE_MILES` reference distance? That's the exact hyperbola argument from `paceometer_review.qmd`'s own illustrative tool, checkable against its worked examples. The live indicator is a 4-state traffic light (`nextZoneState`/`ZONE_STATE_LABELS`/`setZoneDisplay` in `js/app.js`; `.zone-indicator.green/.yellow/.red/.limit` in `css/style.css`) — green/yellow/red purely from the time-math above, plus a 4th `"limit"` state (violet, distinct from all three) that overrides everything else once a known posted speed limit is reached, see the speed-limit-lookup entry below. Each state shows a big word, a big color-matched number, and a caption — never a sentence to parse; labels are `TIME ADDS UP HERE` / `GAINS ARE SHRINKING` / `TIME NOT WORTH CHASING` / `AT THE SPEED LIMIT` (red relabeled 2026-08-11, see below — was `NO TIME LEFT TO GAIN` at the time of the comprehension pass just below). **Comprehension-check pass run 2026-08-06** (had sat as an undocumented "pending" note since 2026-07-25 with no tracked follow-up — caught in a CLAUDE.md audit): checked against the standing wording rule above, both for plain comprehension and for whether any label could read as encouraging speeding. Yellow/red/limit passed outright. Green was flagged as the one risk — paired with a "go" color and phrased as a present-tense payoff, `TIME ADDS UP HERE` could plausibly read as "speeding here gets you something," most concerning since this state most often shows up at lower speeds where speeding is riskiest. Alternatives (`TIME STILL LEFT TO GAIN`, a direct parallel to the red label; `SPEEDING WOULD ADD UP HERE`, naming the behavior explicitly with a conditional "would") were drafted and presented; the user confirmed the existing `TIME ADDS UP HERE` reads as neutral/informational to them, not encouraging, so all four labels were unchanged at the time — green is still unchanged today; red was not, see the entry below for why "red passed outright" here turned out to be an incomplete check.

**Red label fixed 2026-08-11, council review — `docs/TODO.md` Tier 7**: the 2026-08-06 pass above checked red only against the two standing wording rules (comprehension in isolation, encouragement risk) and passed it — but never cross-checked the label against the *number* rendered right next to it, the actual bug. `NO TIME LEFT TO GAIN` claimed zero; the number underneath in this state is the same `marginalSecondsSaved` value every zone state shows, real and nonzero here (e.g. "1:04" is an entirely normal red-state reading — it's just below whichever `ZONE_THRESHOLD_PRESETS` threshold is active, not zero). A driver could read the label and the number as contradicting each other, or misread the number as a gain worth having. Fixed, not just reworded: the number itself is untouched (it's this app's core Core Function metric, deliberately shown identically at every zone state — see above — so suppressing or zeroing it specifically for red would break that design and lose real information near the boundary), only the label changed to stop claiming zero.

First candidate presented and picked by the user, `NOT WORTH CHASING`, was itself caught by a `copy-reviewer` agent pass (this app's dedicated driver-facing-copy review agent) as the one zone label with no explicit noun — every sibling label names its own subject (`TIME` ADDS UP HERE, `GAINS` ARE SHRINKING, AT THE SPEED `LIMIT`), and "chasing" *what* only resolves once a driver also reads the smaller caption line below it, a real gap for a HUD element meant to be read at a glance. Fixed to **`TIME NOT WORTH CHASING`**, restoring the referent (`TIME`, matching green's own label) while keeping the chosen "not worth chasing" framing. The copy-reviewer confirmed the framing itself passes both standing rules: no plausible encouraging-to-speed reading, and no zero/nonzero contradiction with the number the way the old label had. Verified live via the existing `dashboard.spec.js` red zone-state screenshots (light/dark × portrait/landscape, re-run after each wording change) — the two-line wrap at this length fits cleanly inside the zone box in both orientations, no overflow.

`ZONE_THRESHOLD_SECONDS` (red/not-red line) and `ZONE_NEARING_THRESHOLD_SECONDS` (yellow/green split, always exactly double the first, same clean-hyperbola-number coincidence as before) are **driver-adjustable as of 2026-07-25** — no longer fixed constants, but `let` bindings set from `ZONE_THRESHOLD_PRESETS` (`standard`/`strict`/`strictest`, 90s/150s/240s) via Settings → Zone Sensitivity, `localStorage`-backed the same way `APPEARANCE_STORAGE_KEY` works. `standard` (90s, ~58.4mph ceiling) is the new default per updated project guidance that the original 60s default ("~73mph, ordinary highway cruising still reads as still helps") wasn't asking for enough of a time payoff. None of the three presets' specific values are literature-derived. `pct_time_in_zone` is still computed off the red/not-red line (now whichever preset is active), and now explicitly excludes `"limit"` samples from the "in zone" side of the ratio (grouped with red) — a judgment call made when the gating was added, not something explicitly specified beforehand, worth revisiting if you want that metric to reflect pure time-math regardless of gating.

`ZONE_HYSTERESIS_SECONDS` (±5s dead-zone, applied independently at both time-math boundaries) prevents flickering when GPS noise puts the driver right at a boundary, and a brief `zone-flash` animation marks the moment the state actually changes (Core Loop's "display confirms the new state"). `SPEED_LIMIT_HYSTERESIS_MPH` (±2mph) does the same job at the `"limit"` boundary.

**Speed-limit lookup and full gating (2026-07-25)**: the zone was previously defined only against the fixed time-savings hyperbola, not the posted speed limit — deliberately, since "speed-limit lookups have no free tier" (confirmed with the professor's collaborator, 2026-07-15). That reasoning no longer holds: `handlePosition` now calls `maybeQuerySpeedLimit(coords, timestamp)` (fire-and-forget, not awaited) which queries OpenStreetMap's free public Overpass API (`SPEED_LIMIT_API_URL`, nearest tagged way within `SPEED_LIMIT_QUERY_RADIUS_METERS`) for a `maxspeed` tag, throttled by **both** distance (`SPEED_LIMIT_QUERY_MIN_DISTANCE_METERS`) and time (`SPEED_LIMIT_QUERY_MIN_INTERVAL_MS`) since the last query, so an ordinary drive doesn't hammer a free public API. Any failure (network error, timeout, no coverage, unparseable `maxspeed` value) resolves `knownSpeedLimitMph` to `null` rather than reusing a stale value — a real fetch failure means the app genuinely doesn't know anymore. `nextZoneState` checks this before the ordinary red/yellow/green math and can override it entirely: once at/above a known limit, the app never suggests "still helps," full stop, regardless of what the pure time-savings math would say (e.g. a school zone below the zone-ceiling speed). This is an **explicit, discussed exception** to the privacy invariant below — the driver's current lat/lng is sent transiently to Overpass on each throttled lookup, never stored, never sent to Supabase, never logged — not something to silently extend to other third-party lookups without the same conversation. Confirmed via a direct browser fetch test that Overpass has no CORS restriction, but real-world coverage/accuracy/latency of the public instance hasn't been verified against an actual drive.

**Two real bugs found and fixed in the 2026-07-25 speed-limit-gating work (fixed 2026-07-26)**, both discovered by dogfooding rather than code review alone:
1. `timeSavedBySpeedingSeconds`/`timeSavedBySpeedingSoFar` had the subtraction backwards — `limitTrackedSeconds − idealSecondsAtLimit` instead of `idealSecondsAtLimit − limitTrackedSeconds`. Since driving faster than the limit makes `limitTrackedSeconds` *smaller* than `idealSecondsAtLimit`, the old formula went negative and got `Math.max(0, …)`-clamped to a flat `0s` on every trip that actually sped, regardless of how much. Caught by the user running a real simulated drive with a low sim speed limit and getting a suspicious `0s`.
2. `nextZoneState` could get permanently stuck in `"limit"`: if `knownSpeedLimitMph` reverted to `null` (Overpass timeout, rate-limit, or leaving mapped coverage) while the *previous* zone state was `"limit"`, none of the function's transition branches matched a `previous` of `"limit"` once the limit itself was unknown again, so the display (and `pct_time_in_zone` accumulation) froze on `"AT THE SPEED LIMIT"` for the rest of the trip. Fixed by resetting `previous` to `null` at the top of `nextZoneState` whenever `previous === "limit" && knownSpeedLimitMph === null`, before the rest of the gating logic runs. Confirmed via an isolated re-implementation-free test (copy the exact function into a throwaway `.mjs` and drive it with scripted inputs — the same technique to reach for when `document`-coupled module code can't be imported directly in Node) and, unplanned, live in the browser: a real Overpass 503 fired mid-test from repeated querying and the app recovered correctly instead of freezing.

Also surfaced by an end-to-end test against real OSM data (not the simulated-drive override): the Overpass query's `around:30` radius doesn't check the fix's `coords.accuracy` at all (unlike `MAX_FIX_ACCURACY_METERS` elsewhere in this same function), and picks whichever tagged way Overpass returns first within that radius, not necessarily the geometrically nearest one — both are real accuracy risks worth knowing about before trusting the "limit" state on an actual drive, not yet fixed. Separately, the free public Overpass instance visibly rate-limits (`503`) under a burst of queries in a short window — expect that in real-world use, not just heavy testing.

**Speed-limit lookup resilience: mirrors, wide-radius retry, confirmed-reading cache (2026-07-27)**: real-drive testing (first drive with this feature live) confirmed the lookup is accurate whenever it has coverage, but coverage itself is spotty — expected, since it's a direct function of OSM's `maxspeed` tagging completeness and no client-side change adds tags that don't exist. Three additions narrow the gap without ever inventing a number OSM doesn't have, all in the same speed-limit block in `js/app.js`: (1) `SPEED_LIMIT_API_URLS` is now an array of three public Overpass mirrors (`overpass-api.de`, `overpass.kumi.systems`, `overpass.openstreetmap.fr`); `queryOverpass()` tries them in order and moves on from a non-ok response or a network/timeout error rather than failing the whole lookup — addresses the rate-limiting/`503` issue noted just above. (2) `fetchSpeedLimitMph()` retries once at `SPEED_LIMIT_QUERY_RADIUS_WIDE_METERS` (100m, up from the base 30m) if the tight radius comes back empty across every mirror, since some "no result" cases are a tagged way sitting just past the original radius. (3) `speedLimitCache` remembers each *confirmed* (real OSM tag, never inferred) reading for `SPEED_LIMIT_CACHE_MAX_AGE_MS` (5 min) within `SPEED_LIMIT_CACHE_RADIUS_METERS` (120m); `maybeQuerySpeedLimit()` falls back to `cachedSpeedLimitNear()` when a fresh lookup comes back empty, so a brief gap between successful lookups — or re-driving an already-queried stretch — doesn't blank the sign even though nothing about the road changed. The cache is in-memory only, per session, same as `lastSpeedLimitQuery` already was — no new persistence, no change to the privacy invariant below. None of this has been verified on an actual drive yet (only syntax-checked and smoke-tested that the app still loads) — a paid speed-limit API remains the only real fix for coverage itself, noted as a known limitation until that's in budget.

**Always-on speed limit sign (2026-07-26, redesigned 2026-08-06)**: `#speed-limit-sign`/`#speed-limit-sign-value` in `index.html`, `setSpeedLimitSignDisplay()` in `js/app.js`, called from `handlePosition` every fix. A permanent corner-anchored HUD element (top-right, mirroring `.settings-nav`'s top-left placement/margin) showing whatever `knownSpeedLimitMph` currently is — the same value the zone-gating logic already tracks, just surfaced directly instead of only implied by the `"limit"` zone state. Styled as a literal white/black road sign (`.speed-limit-sign`/`.speed-limit-sign-label`/`.speed-limit-sign-value` in `css/style.css`) and **deliberately not theme-colored** — a real sign doesn't change appearance in dark mode, and staying visually literal is what makes it instantly readable at a glance. Hidden entirely (not a `"--"` placeholder) whenever no limit is known. This is a real feature under consideration for shipping, not a dev tool — unlike the simulated-drive block, it does not appear on the pre-launch removal checklist below.

**Redesign (2026-08-06, raised in live testing)**: the original was a circular white badge with a red ring — reads as a European-style sign, not the rectangular white/black one US drivers actually recognize at a glance, undermining the whole point of surfacing it directly. Rebuilt as a literal US-style sign: white rectangle, solid black border, "SPEED"/"LIMIT" stacked on two lines exactly like the real sign (crammed onto one line would've been less recognizable, not just less authentic), large black number. **Wording standing rule (2026-07-26)**: beyond the existing "confirm actual comprehension, don't ship a single best-guess rewrite" standard (see the wording-revision history above), any copy touching time-saved-by-speeding, speed itself, or the zone/limit state must also pass a second check: *could a driver read this as encouragement to go faster?* The live in-trip line and the end-of-trip headline both used to read as a scoreboard the driver could feel invited to make go up ("Xs faster than the speed limit") — fixed by prefixing both with "only" (`setTripZoneProgressDisplay`/`showTripSummary`, now in `DashboardView`; the end-of-trip version is a smaller `.trip-summary-value-prefix` span, not jammed into the 5rem number itself, so it reads as a qualifier rather than part of the number — built via `createElement`/`append` as of 2026-08-05, previously `innerHTML`, see the Trip recording entry below for why that changed). Correctness of the underlying math does not excuse framing that cuts against the project's reduce-speeding goal — default to language that undersells the gain ("only", "just", "barely") rather than neutral or celebratory phrasing.

**Trip recording is a separate layer on top of the live display**: `recordSample()` only accumulates into `trip` while `recording` is true, i.e. between Start Trip and End Trip taps. The live speed/pace/zone readout runs continuously once signed in regardless of whether a trip is being recorded. `endTrip()` sends the aggregates to Supabase — `avg_speed_mph`/`max_speed_mph`/`min_speed_mph`, `sample_count`, `distance_miles` (integrated from `mph × Δt` between samples, not from lat/lng, so it doesn't violate the privacy invariant below), `avg_pace_seconds` (a genuinely separate running mean of per-sample pace, not derived from `avg_speed_mph` — mean-of-pace ≠ pace-of-mean-speed, so comparing the two after a drive is a sanity check on the pace formula itself), `pct_time_in_zone` (Accessory Feature — the same hysteresis-corrected `zoneState` the live indicator computes, time-integrated over the trip; time below `PACE_MIN_SPEED_MPH` is excluded from both sides of the ratio rather than counted as "out of zone"), and `pct_time_under_limit` (2026-07-25, same exclusion principle but keyed off whether a speed limit was known for that sample — see `trip.limitTrackedSeconds`/`underLimitSeconds` in `recordSample`). Not yet surfaced in any UI (a future trip-history tab is the plan) but populating now. Never a location trace, beyond the transient Overpass lookup described above.

**Bug fixed 2026-08-05**: `tripsApi.js`'s `saveTrip()` read `user.id` straight off `supabase.auth.getUser()`'s result with no null check. An expired access token plus a failed silent refresh (plausible on a longer drive through spotty connectivity — exactly this app's use case) resolves `user` to `null` instead of erroring, and nothing in the call chain (`saveTrip` → `endTrip()` → the trip button's click handler) caught the resulting throw — the trip button stayed permanently disabled and the summary frozen on "Saving…" until a reload. Fixed with an explicit `if (!user) return new Error(...)`, fitting the function's existing return-an-error-or-null contract with no other changes needed. Found in a full-codebase audit, not by reproducing the actual expired-session condition live.

**Bug fixed 2026-08-05**: `DashboardView.showTripSummary()` used `innerHTML` to inject the "only" prefix span, contradicting `docs/TODO.md`'s 2026-07-16 security-audit claim of "no XSS sinks (`textContent` only, no `innerHTML` anywhere)" — not exploitable in practice (the interpolated value is always a `formatDuration()`-formatted number string), but the claim was quietly false the moment this line existed, and a future edit interpolating a less-trusted string into the same call would have silently inherited an XSS-capable sink nobody would think to re-audit. Fixed with `createElement`/`textContent`/`append`; verified the resulting DOM is byte-identical to the old `innerHTML` output.

**`GlobalErrorHandler` class (2026-08-19, council review Tier 7 — `docs/TODO.md`)**: before this, an uncaught exception or rejected promise anywhere in the app just froze whatever was on screen — nothing logged, nothing shown to the driver, no way to tell "the app is genuinely broken" apart from "GPS just hasn't updated in a while." `js/errorReporting/globalErrorHandler.js`'s `GlobalErrorHandler` registers global `window` `"error"`/`"unhandledrejection"` listeners (module-agnostic by design — a bug anywhere should surface the same way, not just in whichever module happened to add its own try/catch) and, on either firing, logs the real error to the console (for actual debugging, e.g. via remote inspection on a real drive — same reasoning as the wake-lock fix's `console.warn`) and calls a constructor-supplied `onError(message)` callback with one fixed, generic driver-facing message. `app.js`'s composition root instantiates it immediately after `dashboardView` exists (the only thing it needs) and passes `dashboardView.showGlobalError`, so it's live before any other module below gets a chance to throw during its own setup. Deliberately does **not** attempt any recovery itself (retry, state reset, reload) — a genuinely uncaught error means some invariant this codebase assumes broke, and guessing at an automatic fix risks making things worse; the message just tells the driver something's wrong and that a reload is the safe next step, the same escape hatch `showLocationDenied()` already uses for its own unrecoverable state.

`DashboardView` gained `showGlobalError(message)`/`hideGlobalError()` (a new `#global-error-banner` element, dismissible via its own button) — deliberately **not** modeled on `showLocationDenied()`'s inline-swap pattern: an uncaught error might have nothing to do with whatever's currently on screen, so hiding `#readout`/`#trip-controls`/etc. underneath it would make things worse, not better, if the rest of the app is actually fine. Instead it's a small, non-blocking, `position: fixed` overlay sitting *outside* every `.screen` div in `index.html` (unlike `#feedback-panel`, which is `position: absolute` and scoped inside `#app`), so it's visible no matter which screen is showing when the error fires — auth, settings, trips, or the live dashboard. **Real layout bug caught by an actual screenshot, not assumed safe from the CSS alone**: the first version's bottom-anchored, stacked (message-then-Dismiss) layout was tall enough in landscape's much shorter viewport to visibly overlap the auth screen's submit button — confirmed by literally screenshotting it, not by reading the rule. Fixed with a landscape-specific override (`@media (orientation: landscape)`) reverting to a single compact row with smaller text/padding, verified to no longer overlap in either screen. On the live dashboard specifically, the banner still touches the bottom edge of the zone-caption card in landscape — a real but accepted visual trade-off, not fixed further, since it never covers an actual interactive control (Start Trip, the corner nav icons) and the banner is dismissible.

**In-progress-trip localStorage checkpoint (2026-08-11, council review Tier 7 — `docs/TODO.md`)**: `Trip` previously held every accumulator field only in memory, so a page reload, the phone killing a backgrounded tab, or a crash mid-drive lost the whole trip with zero recovery — a real risk given "trips are the actual data being collected." `js/trip/trip.js` now mirrors its `_trip` accumulator object to `localStorage` (`paceometer-in-progress-trip`) on `start()` and every `recordSample()`, and clears it on `finish()`/`cancel()` — only the same derived scalars this class already holds (sample counts, sums, distance, etc.), never raw lat/lng, staying within the standing privacy invariant. `js/app.js`'s `startApp()` now calls a new `resumeTripIfAny()` on every genuine sign-in/restored session (same `SIGNED_IN`/`INITIAL_SESSION`-only gating `AuthController` already uses, so this never fires on a token refresh mid-drive): if a checkpoint exists, is recent enough, and belongs to the currently signed-in user, `Trip.restoreFrom()` puts the driver right back into an actively-recording trip — the button already reads "End Trip" the moment the dashboard renders, with no separate recovery UI or driver-facing message (matches the existing 2026-07-21 "no separate status text" declutter call).

Three deliberate safety gates, not oversights:
1. **Staleness cutoff** (`MAX_RESUMABLE_TRIP_GAP_MS`, 3 hours, a project design choice like `ZONE_THRESHOLD_PRESETS` — not literature-derived): generous for a real crash-and-quickly-reopen, but short enough that a truly abandoned trip (app not reopened until the next day) doesn't get silently resumed against a meaningless elapsed time. Checked against `lastWrittenAt` (stamped on every checkpoint write), not `startedAt` — what matters is how long ago the app was last confirmed alive, not how long the trip itself has nominally been running.
2. **Cross-account safety**: the checkpoint is scoped by the signed-in driver's user id (`Trip.start(userId)`, read via a local, non-network `supabase.auth.getSession()` call in `app.js`'s `startTrip()`/`resumeTripIfAny()` — `Trip` itself stays Supabase/user-concept-unaware, just holds whatever id it's handed). A shared device signing in as a different person than whoever left the checkpoint behind gets it silently discarded (`Trip.clearCheckpoint()`), never resumed — the exact class of bug already found and fixed once for `VehiclePicker`'s cached vehicle selection (2026-08-05, see that entry above).
3. **Demo trips never checkpoint at all**: `Trip`'s constructor takes a `checkpointing` flag (default `true`); `SimulatedDrive`'s separate `_demoTrip` instance passes `false`. Without this, a crash mid-demo would have left fabricated simulated-driving data in the same checkpoint slot, and the next real app load would have tried to "resume" it as if it were genuine driving — worse than the bug this feature exists to fix, caught during design before it was ever wired up wrong.

`recordSample()`'s distance/zone-time integration measures the gap since the *previous recorded* sample (`trip.lastSampleTimestamp`) — `restoreFrom()` deliberately resets that field to `null` rather than carrying the pre-crash timestamp forward, so the first real sample after a resume takes the same "first sample of a trip, skip integration" path every genuine first sample already does, rather than integrating `mph × (a multi-second-to-multi-hour gap)` as if the driver held that speed the entire time the app was closed.

A narrow race is closed with one line, not left open: `startApp()` disables `#trip-btn` for the brief async window `resumeTripIfAny()` needs (a `Trip.readCheckpoint()` local-storage read plus one non-network `getSession()` call), re-enabling via `.finally()` regardless of outcome — otherwise a tap on Start Trip during that window could call `trip.start()` and silently overwrite a still-loading resumed trip before it lands. The common case (no checkpoint) clears this within a microtask, imperceptible in practice. `startTrip()` itself is now `async` for the same reason (it also reads the signed-in user id via `getSession()` before calling `trip.start()`) and disables the button around that same brief window, closing an equivalent rapid-double-tap race on the normal start path.

Verified live via an instrumented Playwright Chromium session (ad hoc, not part of the checked-in suite) confirming the checkpoint's shape, then formalized as `tests/e2e/specs/tripCheckpoint.spec.js`: a real trip resumes after a reload (button already reads "End Trip", confirmed via a real screenshot) and the checkpoint clears on `finish()`; a checkpoint fabricated under a different user id is discarded; a checkpoint fabricated 4 hours old is discarded; a checkpoint fabricated fresh under the real signed-in user's id (extracted from the test account's own saved session JWT) resumes correctly even without ever having been written by the app itself; and a simulated drive never touches the checkpoint key at all, during or after the run. `docs/diagrams/class-diagram.puml` updated in the same change (`Trip`'s new `userId`/`checkpointing` fields and `start(userId)`/`restoreFrom`/the two static checkpoint methods; `App`'s new `pendingSaveSummary` field and `attemptSaveTrip`/`resumeTripIfAny` private methods — the latter two were a gap from the trip-save-retry entry just above, caught and fixed while touching this diagram for the checkpoint work rather than left for later) and `package-diagram.puml` (`app.js` now imports `supabaseClient.js` directly, for the local `getSession()` calls both features above use) — both PDFs regenerated and visually confirmed.

**Fuel-cost trip summary (2026-08-03)**: extends the existing time-saved-by-speeding number with a second, complementary one: roughly what the trip cost in gas, and roughly how much of that came from driving over the speed limit. `js/ui/vehiclePicker.js`'s `VehiclePicker` class is a cascading Make → Model → Year → Variant picker in the Settings screen. There's no separate "trim" column in fueleconomy.gov's data, so "Variant" is built from whichever of `trany`/`drive`/`displ`/`cylinders` distinguishes rows sharing the same make/model/year. It's backed by the `vehicle_fuel_economy` Supabase table and resolves to a single `{ cityMpg, highwayMpg, label }` object cached in `localStorage` (`paceometer-vehicle`), resolved once and used directly, the same style as `ZONE_THRESHOLD_PRESETS`.

**Bug fixed 2026-08-05**: that `localStorage` cache is per-origin, not per-account, and the app never reloads the page between sign-out/sign-in (`AuthController` just toggles screen visibility) — so a second person signing in after a first person signed out silently inherited the first person's selected vehicle, and their trip would save to Supabase (`vehicle_label`/`gallons_used`/`gallons_saved_by_speeding`) computed against the wrong car's MPG, with no indication anything was wrong. Fixed by making `VehiclePicker`'s clear logic public as `clear()` (previously private, only wired to the Settings "Clear" button) and calling it from `app.js`'s `stopApp()` — the same session-ending cleanup point `trip.cancel()` already uses. Found in a full-codebase audit; verified live by setting a fake vehicle in `localStorage`, signing out, and confirming it read back empty. A plain editable `paceometer-gas-price` setting (default verified against AAA's national average on 2026-08-03, not a claim about the driver's actual local price) converts gallons to dollars in `app.js`, keeping `DashboardView` a "dumb" renderer of already-converted numbers.

`js/math/fuelMath.js`'s `gallonsPerMile(mph, cityMpg, highwayMpg)` is the only new formula, mirrored in `python/paceometer_math/fuel_math.py` and golden-vector-tested (`tests/golden_vectors/fuel_math.json`) exactly like the pace/zone math. The dataset only gives two real data points per vehicle: EPA city (21.2mph test average) and highway (48.3mph test average) MPG, both confirmed directly against fueleconomy.gov's own test-schedule page. So there's no true speed-swept curve to draw from. Between the two anchors, gallons/mile is a straight line (a reasonable interpolant, though the lit review's Wang et al. 2008 finds the real minimum sits around 31-43mph, inside this range). **Above the highway anchor, where most real speeding-over-the-limit driving happens, a straight line through just the two anchors keeps improving mileage as speed rises.** That's backwards, and it would have told a driver they saved gas by speeding in the most common real case. Found and fixed the same session it was specced, caught before shipping, not after. Fixed by growing gallons/mile quadratically above that anchor. The v² *shape* is ordinary aerodynamics (drag force ∝ v², power to overcome it ∝ v³, so fuel/mile from drag alone ∝ v²; see `paceometer_lit_review/lit_review.md` section 3), but the specific *coefficient* is only calibrated from a widely-cited rule of thumb (about 10% more fuel at 110 vs. 100 km/h) that the lit review itself flags as needing primary-source verification before academic citation. It's solved algebraically in code, not hardcoded, the same way `zoneCeilingMph` is, so it's easy to replace once a tighter primary-sourced fit (Greene 1981, Wang et al. 2008) is worth the effort. Treat the magnitude as same-ballpark, not exact, until then.

`js/trip/trip.js`'s `Trip` class mirrors its own existing `limitTrackedSeconds`/`idealSecondsAtLimit` pattern for fuel: `actualGallons` covers the whole vehicle-tracked trip (the "what did this cost" number), while `limitTrackedGallons`/`idealGallonsAtLimit` are restricted to samples where a speed limit was *also* known, so the "gas saved by speeding" comparison is apples-to-apples. `gallonsSavedBySpeeding` is clamped at 0 for the same reason `timeSavedBySpeedingSeconds` is: the model isn't strictly monotonic in speed (city-to-highway driving genuinely improves mileage here, matching real EPA data), so a trip driven entirely at or under the limit could otherwise show a small negative "savings," which would read as encouraging speeding and violate the wording standing rule above. **Wording reviewed 2026-08-08** (`DashboardView.showTripSummary`, `#trip-summary-gas-cost`/`#trip-summary-gas-saved`, via the `copy-reviewer` agent — see `docs/TODO.md`). The total-cost line (`"~$X in gas this trip"`) passed both standing checks outright. The second line originally read `"only ~$X of that from driving over the limit"` and failed the never-encourages-speeding check: `"only"` is this app's standing prefix for underselling a *benefit* (see the headline "faster than the speed limit" line), but `gasCostSavedUsd` — despite its variable name — is always a *cost* (the extra gas burned from speeding, clamped at 0 exactly so it can never read as "you saved money by speeding," per the paragraph above). Applying "only" to a cost figure inverted the intended effect: it read as "speeding barely cost you anything," reassurance rather than a deterrent — the mirror-image of the original "behind the fastest pace" mistake, wrong framing polarity rather than wrong math. Fixed to state the extra cost plainly: `"~$X of that was extra, from driving over the limit"`. Verified live (a real simulated highway drive with a vehicle selected and a low speed-limit override) that both lines render and wrap correctly inside the cost card, not just checked as a string in isolation.

The `vehicle_fuel_economy` table (`supabase/migrations/20260803183109_...sql`) is the **first table in this schema that isn't per-user**. It's shared reference data, RLS-enabled with a single `select`-for-`authenticated`-`using (true)` policy and no insert/update/delete policy for that role at all, since only the weekly refresh Action (via a service-role key, which bypasses RLS) ever writes to it. Don't copy the `trips` table's `auth.uid() = user_id` pattern here; there's no `user_id` column and there shouldn't be one. `trips` itself gained `gallons_used`/`gallons_saved_by_speeding`/`vehicle_label` (`supabase/migrations/20260803183130_...sql`). `vehicle_label` is a plain text snapshot, not a foreign key, so a past trip's summary stays meaningful even if that exact vehicle row changes in a later refresh or the driver switches cars.

**Bug found running the pipeline for real the same day**: the first version of the table's migration only granted `select` to `authenticated`, so the weekly refresh script's first live run failed with `permission denied for table vehicle_fuel_economy` even though the service-role key itself was valid. `service_role` bypasses RLS, but bypassing RLS and holding an ordinary table-level `GRANT` are separate things in Postgres; RLS bypass alone doesn't imply `SELECT`/`INSERT`/`UPDATE` privileges. Fixed in a follow-up migration (`supabase/migrations/20260803193402_grant_service_role_on_vehicle_fuel_economy.sql`): `grant select, insert, update on public.vehicle_fuel_economy to service_role;`. This is the second time the "Automatically expose new tables is off" trap (see the Supabase access model entry below) has bitten this project, and the first time it's shown up per-role rather than per-table: a new table needs the grant repeated for every role that touches it, not just once.

**Second bug found live-testing the vehicle picker, same day**: `VehiclePicker`'s make/model/year queries originally did `select("make").order("make")` across the full table and deduped client-side, which silently hit PostgREST's default 1000-row response cap -- a cap that applies even with `.order()`. At 48,524 rows and ~150 distinct makes (roughly 300+ rows per make), 1000 rows barely got past the A's, so the Make dropdown only ever showed about 7 options. Popular long-running models (e.g. a nameplate sold across 40 years with many trims per year) could hit the same cap on the model-list query too. Fixed by moving the `DISTINCT` server-side instead: three plain SQL functions (`supabase/migrations/20260803194803_add_vehicle_lookup_functions.sql` -- `vehicle_fuel_economy_makes()`, `vehicle_fuel_economy_models(p_make)`, `vehicle_fuel_economy_years(p_make, p_model)`, all `security invoker` since `authenticated` already has direct `select` on the table) that each return only the handful of rows actually needed, called via `supabase.rpc(...)` in `js/ui/vehiclePicker.js` instead of `.from(...).select(...)`. The year-level query wasn't changed to fetch full variant rows (`_onYearChange`) since a single make+model+year combination is inherently small -- no cap risk there.

**Third bug, same testing pass**: the four-select `.vehicle-picker` grid overflowed the viewport on narrow screens. CSS Grid items default to a min-width based on their content's intrinsic size, and a `<select>`'s intrinsic width is driven by its longest `<option>` text ("American Motors Corporation") -- that beats the `1fr` track sizing unless the item is explicitly told it can shrink below its content width. Fixed with `min-width: 0` on `.vehicle-select` (`css/style.css`).

**Searchable Make/Model/Year/Variant dropdowns (2026-08-04)**: with ~150 makes and some models spanning 40+ model-years, scrolling a plain `<select>` to find one entry was painful. `js/ui/searchableSelect.js`'s `SearchableSelect` class replaces each of the four `<select>`s with an autocomplete-style combobox: a text input that opens its own filtered popup `<ul role="listbox">` directly (focusing shows the full list; typing filters it live, case-insensitive substring match), not a search box layered above a still-native dropdown. **Metric/imperial unit display (2026-08-07, Tier 3.5)**: a new Settings → Units toggle (`#unit-system-switch`, `paceometer-units` in `localStorage`, default `"imperial"`, same `SegmentedSetting` pattern as Appearance/Zone Sensitivity/Sound). This is a **display-only** concern by design — every value this app actually computes with (`Trip`'s accumulators, the zone-threshold math, `gallonsPerMile`, everything written to Supabase) stays permanently mph/miles/gallons regardless of this setting, exactly as before. Conversion happens only at the display boundary, via the new `js/math/unitsMath.js` (`mphToKmh`, `milesToKm`, `gallonPriceToLiterPrice`/`literPriceToGallonPrice` — plain linear conversions by a fixed constant, deliberately **not** mirrored in `python/paceometer_math/` with a golden-vector oracle the way the derived formulas are, since there's no derivation-drift risk in a fixed multiply the way there is in e.g. `zoneCeilingMph`'s algebraic solve; see that file's own header). `DashboardView.setUnitSystem()` stores the current choice and every render method that shows a speed/distance already-mph value converts right before displaying it (`setSpeed`, `renderZone`'s captions, `showTripSummary`'s distance line); `TripHistory` takes the same `getUnitSystem` callback pattern `getGasPricePerGallon` already established, converting `distance_miles`/`avg_speed_mph` per card. `setPace()` is the one exception to "just convert the same number" — see its own entry below. The gas-price setting (`app.js`) stays canonically stored as $/gallon either way (no conversion is needed to turn gallons into a dollar cost), but the input's displayed/edited value and its label (`#gas-price-label`, now has an `id` for exactly this) switch to $/liter in metric, converting at that one input boundary.

Two deliberate exceptions, not oversights:
1. **The always-on `#speed-limit-sign` stays mph regardless of this setting.** It's built to mimic a literal, physical US road sign (see that entry above) — real US signs are always posted in mph, so converting the number shown here to km/h would make it stop matching what's actually posted on the road next to the driver, undermining the entire point of that element. The **zone-indicator's "posted limit: ~Xmph" caption** (`renderZone`, a different element — the app's own live narration, same family as the speed/pace readout) *does* convert, since it's this app's own instrument-cluster text, not a sign replica.
2. **The Settings → About section's literature-citation prose stays in miles/mph, unconverted.** "Minutes to cover 10 miles" and "10mph faster" there are describing Peer & Gamliel (2013)'s actual published reference distance/increment as the paper defines them — converting that prose to a km-equivalent would misrepresent what the citation actually says, the same traceability concern this file's math sections already hold formula changes to.

**The pace readout's "/ 10mi" suffix was revised the same day, raised as confusing**: the first version relabeled it to its literal km-equivalent, `milesToKm(PACE_REFERENCE_MILES).toFixed(1)` = "16.1km" — technically accurate (10mi really is 16.09km) but an odd, overly-precise number to read at a glance, and worse, it was still displaying the time to cover 10 *miles* next to a "16.1km" label that a metric-preferring reader would reasonably take at face value as 16.1km, not notice was a mile-based figure underneath. Fixed by making metric mode a **genuinely separate calculation** instead of a relabeling: `unitsMath.js`'s `PACE_REFERENCE_KM = 10` (an independent, round-number design choice for metric mode, not a conversion of `PACE_REFERENCE_MILES` — same status as `ZONE_THRESHOLD_PRESETS`, not a literature figure) and `paceSecondsForKm(kmh)` compute the real time to cover an actual 10km, using the same `t = d/v` shape `paceSecondsFor()` uses for the literature's 10-mile figure, not that function's output converted. The two unit systems now show genuinely different numbers for the same real speed by design (60mph: "10:00 / 10mi" imperial vs. "6:13 / 10km" metric) — each is an honest answer to "how long to cover *this system's own* clean reference distance," not two labels on one shared computation. `DashboardView.setPace()` still gates on the real, unconverted mph via `paceSecondsFor(mph) !== null` (`PACE_MIN_SPEED_MPH`) regardless of unit system — that threshold is about when the concept stops being meaningful at very low real-world speed, not something that depends on which reference distance is being displayed.

**The zone caption's "+16km/h" is a different case, deliberately left as the literal conversion, not a matching round-number fix**: raised as the same complaint right after the pace fix above, and it looks identical on the surface (`ZONE_SPEED_INCREMENT_MPH = 10` converts to a non-round 16.09→16km/h, the same shape as the pace bug did) — but the fix isn't the same, and applying it would have been a real mistake. Pace's reference distance is a free, display-only benchmark; nothing else in the app depends on which number it is. `ZONE_SPEED_INCREMENT_MPH` is not that — it's the literal input to `marginalSecondsSaved()`, the function that decides the actual green/yellow/red zone state, this app's core safety feature. Giving metric mode its own independent round increment (mirroring the pace fix) would mean the traffic light could show a different color at the *exact same real driving speed* depending only on which unit system the driver has selected — a real change to core app behavior, not display polish, and exactly the kind of change this file's Core Function/zone-math sections already treat as needing to stay traceable and consistent. Explicitly raised and confirmed with the user (2026-08-07): classification stays identical in both unit systems (always the real +10mph/16.09km/h), so the caption is deliberately an honest, if not perfectly round, conversion — see `defaultZoneCaption()`'s own comment in `js/ui/dashboardView.js` for the full reasoning, written specifically so this doesn't get "fixed" again by mistake later.

The dev-only simulated-drive tool (`js/dev/simulatedDrive.js`'s `#simulate-speed-limit` placeholder and `#simulate-manual-speed` readout) also stays mph-labeled regardless of the Units setting — not user-facing (gated behind `?dev`), so not worth the same treatment; a deliberate scope call, not a gap.

**Voice feedback / bug report (2026-08-07, Tier 3.6)**, modeled on Tesla's in-car voice feedback: `#feedback-nav`, a third icon in the same top-left corner stack as `settings-nav`/`trips-nav`. Tap to start recording, tap again (or a 30-second cap, `MAX_RECORDING_MS`) to stop — `js/ui/feedbackRecorder.js`'s `FeedbackRecorder` class owns the whole flow. Deliberately does **not** hide `#readout`/`#trip-controls` the way Settings/Trip History do — the point is leaving feedback without losing sight of the live speed/zone readout while driving, so it only ever shows a small non-blocking `#feedback-panel` status banner (recording/transcribing/sent/error text) over the dashboard.

**Privacy architecture, decided explicitly before writing any code**: this was raised as a real privacy-invariant question, not defaulted silently — voice audio is a bigger step up from this app's "no raw GPS ever" stance than anything shipped so far, being more directly identifiable than a lat/lng ever was. Landed on **transcript-only, never raw audio stored** — `MediaRecorder` records a clip client-side, it's sent once to a new Supabase Edge Function (`supabase/functions/transcribe-feedback/`), which forwards it to Groq's Whisper API (`whisper-large-v3-turbo`) using a server-side-only `GROQ_API_KEY` secret and returns just the transcript text. The audio is never written anywhere — not client-side beyond the one upload, not in the Edge Function (held in memory only for the single outbound `fetch` to Groq, discarded when the response returns), not in Supabase. Only `js/trip/trip.js`'s recorded metrics and the fuel-economy table have ever needed a genuinely new privacy-surface conversation before this (the Overpass speed-limit lookup's transient lat/lng send); this is the same category of decision, made the same explicit way.

Chose `MediaRecorder` (broadly supported — Chrome/Firefox/Safari all implement it) over the browser's built-in `SpeechRecognition` API specifically because `SpeechRecognition`'s cross-browser support is inconsistent (solid in Chrome, historically weak on Safari/iOS) — given this app's stated Chrome/Safari/Firefox/Edge/Brave support matrix, a universally-supported recording API plus a reliable server-side transcription call was judged the safer bet over a client API with known gaps on an entire platform family. Verified directly against primary sources before committing to Groq, not from aggregator summaries: [Groq's own rate-limit docs](https://console.groq.com/docs/rate-limits) confirm the free tier gives Whisper 2,000 requests/day and 28,800 audio-seconds/day (8 hours) — far more than a friends-and-family feedback feature will ever use — and [Supabase's Edge Function invocation limit](https://github.com/orgs/supabase/discussions/37060) is 500,000/month on the free plan, also not a real constraint at this scale.

**Why a Supabase Edge Function exists at all** (the first one in this project — nothing else here has needed server-side compute beyond Postgres/RLS and the weekly fuel-pipeline GitHub Action): a Groq API key can't be shipped in client-side JS, same "never ship a secret to the client" rule already followed for the Supabase service-role key. The function (`supabase/functions/transcribe-feedback/index.ts`, Deno) is a thin, stateless proxy — receives the audio as `multipart/form-data`, forwards it to Groq, returns `{ text }`. Auth is enforced by Supabase's own default behavior (functions require a valid JWT unless deployed with `--no-verify-jwt`, which this one deliberately isn't) — no separate auth check needed in the function's own code, same as RLS being the real access boundary elsewhere in this project rather than key secrecy. CORS was originally wide open (`Access-Control-Allow-Origin: *`) since the JWT requirement is the actual gate, not origin-checking — tightened to an explicit allow-list the same day during a security-review pass, see below. Verified locally without Docker (Supabase's usual local Edge Function dev path) by running the function directly with `deno run --allow-net --allow-env` and hitting it with `curl` — confirmed the OPTIONS preflight, the missing-file 400 path, and that a real multipart upload correctly reaches Groq's real endpoint (rejected only because the smoke-test used a fake key, not a client-side format/transport bug).

`FeedbackRecorder` takes `getZoneState`/`getIsRecordingTrip` callbacks into `app.js`'s own state (same pattern as `getGasPricePerGallon`/`getUnitSystem` elsewhere) and snapshots them into the `feedback` table's metadata columns (`zone_state`, `is_recording_trip`, `user_agent`) at the moment feedback is sent — analogous to Tesla's own system-state snapshot, but deliberately **not** including raw lat/lng, consistent with the standing privacy invariant. `supabase/migrations/20260807221842_add_feedback_table.sql` adds the table: `authenticated` can `insert` their own rows (RLS, `auth.uid() = user_id`) and `select` them back (granted for consistency with every other per-user table in this schema, though no UI reads it today); no `update`/`delete` policy, since feedback is a one-way "send it and it's sent" action, same as Tesla's own version — only the developer can remove a row, via the dashboard or a service-role query.

Mic-permission handling is deliberately simpler than the geolocation-denied case: any `getUserMedia` failure (permission denied, no microphone present, device busy) shows one message via `#feedback-panel` rather than a dedicated full-panel state like `showLocationDenied()` — the specific cause doesn't change what the driver needs to do (check the browser's site/mic settings), and unlike missing location, missing mic access doesn't block the app's core function, so a lighter-weight, dismissible inline message is proportionate. `cancel()` (called from `app.js`'s `stopApp()`, alongside `trip.cancel()`/`simulatedDrive.stop()`) stops and discards an in-progress recording and releases the mic if the driver signs out mid-recording — bypasses the normal stop-and-send path entirely rather than stopping then discarding after the fact, so a signing-out driver's recording is never transcribed or sent.

**Security-review hardening (2026-08-08)**: a full `app-security-audit` pass (see `docs/SECURITY_TODO.md` for the complete checklist) found this Edge Function was the one real piece of new attack surface with gaps — a signed-in-only gate still let any account call it an unlimited number of times against Groq's *shared, project-wide* daily quota, with no cap on the forwarded file's size either. Both fixed in the same file: a per-user rate limit (10 submissions/hour, checked via a Supabase client constructed with the *caller's own* Authorization header — not the service role — so the existing `feedback: users select own` RLS policy scopes the count query to their own rows automatically, same identity-from-session principle as everywhere else in this app) returning 429 past the threshold; and a 10MB file-size cap checked before the file ever reaches Groq. The rate-limit check fails **open** on its own query error (a network blip) rather than blocking a legitimate submission over an unrelated hiccup — the cap is a courtesy limit on casual/accidental abuse, not the only thing standing between this project and a real attacker, so failing open here is a reasonable trade. `js/ui/feedbackRecorder.js` reads `error.context.status` (the raw fetch `Response` `supabase-js`'s `FunctionsHttpError` carries — confirmed directly against the `@supabase/functions-js` source, not assumed) to show a specific "too many submissions" message and hide the Retry button on a 429 specifically, since retrying immediately would just hit the same limit again. CORS also tightened from a wildcard to an explicit origin allow-list (the real GitHub Pages origin plus `localhost:8000`/`127.0.0.1:8000`) — a bare production-only origin would have silently broken every local test run, since this project is routinely tested locally against this exact real Edge Function, never a mock. Same pass added `NOT VALID` `CHECK` constraints to `trips`/`feedback` (`supabase/migrations/20260808045856_...sql`) — RLS restricts *who* writes a row, not *what* they write; `NOT VALID` enforces the constraint on every future write without scanning (and risking a failed migration against) the already-live rows. All of it verified locally (`deno run` + `curl`, no Docker) before ever handing off a deploy — a real 11MB file correctly rejected before reaching the rate-limit check or Groq, an allowed `Origin` header echoed back correctly, a disallowed one falling back to the production origin so the browser blocks it client-side. All confirmed live the same day: `supabase migration list` shows local/remote in sync, and a real `curl` against the deployed function confirmed the new CORS allow-list and Supabase's own JWT gate (`UNAUTHORIZED_NO_AUTH_HEADER` on an unauthenticated request, returned by the platform before the function's own code ever runs) are both active.

**Content-sniffing added (2026-08-19, third security-review pass — `docs/SECURITY_TODO.md`)**: the existing `ALLOWED_AUDIO_TYPES` check validated only the *declared* `audioFile.type` — a string the client sets in the multipart request and the server never independently verified, so a crafted request could claim `audio/webm` for arbitrary non-audio bytes. Two gotchas worth knowing if you touch appearance-related CSS: (1) the `@media (prefers-color-scheme: light)` block's plain selectors (`body`, `.zone-indicator.*`, etc.) have the *same* specificity as base rules setting those properties elsewhere in the file, so it must stay physically *after* them in `css/style.css` (it's kept at the very end) to win on source order — an attribute-scoped `:root[data-theme=...]` selector doesn't have this problem, since it outranks a plain `:root` on specificity regardless of position, but the plain `@media` block does; moving it back up silently breaks system-light detection. (2) Any per-appearance token that's a `color-mix()` formula referencing `--text-secondary`/`--text-primary` (like `--extra-tint`) recomputes differently in light vs. dark since those change — a formula validated in one appearance isn't automatically safe in the other; see the accessibility entry below for a real bug this caused.

**Supabase access model** (see `supabase/migrations/`): the project was created with "Automatically expose new tables" turned **off**, so any *new* table needs an explicit `grant select, insert on public.<table> to authenticated;` or the API will reject all access to it regardless of RLS policies — this is a common silent-failure trap when adding tables. RLS policies scope both `insert` and `select` to `auth.uid() = user_id`, so each signed-in user can only write/read their own rows; nothing is granted to the `anon` role at all, so unauthenticated requests are rejected before RLS even runs. Only the developer (via the Supabase dashboard or a service-role key, which must never be added to client code) can see the full table across users. The anon key hardcoded in `js/supabaseClient.js` is safe to have committed — RLS is the actual access boundary, not key secrecy. `vehicle_fuel_economy` (added 2026-08-03, see the fuel-cost trip summary entry above) is the one exception to the per-user-row pattern described here: shared reference data every `authenticated` user can `select`, written only by the weekly refresh Action's service-role key.

**Privacy invariant to preserve in any future change**: no raw GPS coordinates ever get sent to Supabase or logged anywhere off-device — only derived scalar metrics. This is a standing project requirement (from the professor meeting that set this architecture), not just current scope; if a change would add a lat/lng field to any outgoing payload, that's a decision to raise explicitly, not make silently. **One explicit, discussed exception exists as of 2026-07-25**: the speed-limit lookup (see above) sends the driver's current lat/lng transiently to OpenStreetMap's Overpass API on each throttled query — never stored, never sent to Supabase, never logged to disk, and disclosed in the Privacy settings section. Any *further* third-party lookup would need the same explicit conversation, not a silent extension of this precedent.

Signup itself is back **on** project-wide; the hook is the actual gate, rejecting any email not in the table with a 403 and a custom message, same contract as Supabase's own documented examples (`{}`::jsonb to allow, `{"error": {...}}` to reject). No client-facing admin UI for the allowlist — adding someone is one `insert` in the SQL Editor, since only the developer ever does it. `invite_allowlist` follows the same access pattern as `vehicle_fuel_economy`/`signup_networks`-style Supabase examples: no RLS, just `grant all ... to supabase_auth_admin` / `revoke all ... from authenticated, anon, public` — the table is invisible via the client SDK entirely, by grant alone.

**Real bug, found only by an actual live signup attempt, not any static check**: right after shipping this, every signup was rejected — including for emails genuinely in the allowlist. Root cause: this Supabase project silently auto-enables Row Level Security on newly created tables, independent of whether the migration itself ever writes `enable row level security` — `invite_allowlist` got this applied with zero policies defined. That doesn't error; it just makes every row invisible to any role except the table owner. The hook function runs as `supabase_auth_admin` (not the owner), so its `select ... where email = ...` always silently matched zero rows, while every diagnostic *except an actual signup* said everything was fine: calling the function directly from the SQL Editor runs as `postgres` (the owner, bypasses RLS by default, so it looked correct), and `has_table_privilege('supabase_auth_admin', ..., 'SELECT')` only checks table-level GRANTs, not RLS policies, so it also came back `true` despite RLS silently blocking every real row. `select relrowsecurity from pg_class where oid = 'public.invite_allowlist'::regclass;` was the query that actually confirmed it (`true`). Fixed by `supabase/migrations/20260805174458_disable_rls_on_invite_allowlist.sql` (`alter table ... disable row level security`), restoring the table to its original grant-only design intent. Confirmed live with a real signup attempt post-fix — succeeded. **General lesson for this codebase**: table-level GRANTs and RLS policies are independent access gates (same family of trap as the `vehicle_fuel_economy` service_role grant bug and the `trips` update/delete policy-without-grant note above) — verifying one says nothing about the other, and the only check that actually exercises both together is a real call as the specific non-owner role that matters (here, testing via a throwaway/diagnostic row and an actual signup attempt, not just a privilege query).
