# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Paceometer: a real-time in-car pace/speed display, built as an installable Progressive Web App. Part of a research project (with Professor Helveston, GWU) testing whether a pace display (not just a speedometer) reduces speeding. The literature review, research plan, and design justifications live in a **sibling repo**, `/Users/yusuf/paceometer_lit_review` (GitHub `ysfrknzydn/paceometer`) — check `lit_review.md` and `paceometer_review.qmd` there before adding or changing any behavior-design decision (pace formula, display layout, zone thresholds), rather than inventing a rationale. Not every phrase in that repo's `research_plan.qmd` is literature-backed — some (e.g. "optimal zone") are this project's own unresolved design extensions, not cited findings; don't assume plan language implies a citation exists.

## Commands

There is no build step, no bundler, no package.json, and no linter: this is intentional (zero-budget, plain HTML/CSS/JS). There is a test suite (see below) and, as of 2026-08-03, CI (`.github/workflows/tests.yml`, runs on every push/PR). Neither gates the GitHub Pages deploy itself, which is still just "push to `main`."

- **Run locally**: `python3 -m http.server 8000`, then open `http://localhost:8000`. Must be served over HTTP(S) — opening `index.html` directly as a `file://` URL breaks the ES module imports. Geolocation works on `localhost` without HTTPS, but testing from a phone requires the deployed HTTPS URL (a phone hitting your laptop's LAN IP is not a secure context, so geolocation is blocked there).
- **Deploy**: push to `main`. GitHub Pages serves directly from the repo root on that branch — no CI/build step in between. Live at `https://ysfrknzydn.github.io/paceometer-app/`.
- **Sanity-check JS**: after editing any `js/*.js` file, at least syntax-check it. These are ES modules, so a plain `node --check app.js` fails on `import`/`export` — either copy to a `.mjs` file first (e.g. into the scratch dir) and `node --check that.mjs`, or simpler, pipe it through stdin with an explicit module type: `node --input-type=module --check < js/app.js` (no copy needed, works in place).
- **Unit tests (2026-07-31)**: `js/math/` holds the app's pure pace/zone/geo/parsing/fuel formulas (no DOM, no browser APIs) and has real tests -- run with `node --test js/math/*.test.js` (Node's built-in test runner, zero added dependency). A parallel, independently-written Python port lives in `python/paceometer_math/` (dev-only -- never runs in the shipped app, no Pyodide) with its own pytest suite (`cd python && ./.venv/bin/pytest`, or `pip install -r python/requirements.txt` into your own venv first). Both suites check themselves against the same fixtures in `tests/golden_vectors/` (`pace_zone.json`, `fuel_math.json`), so a bug in one language's formula shows up as a disagreement with the other -- regenerate a vectors file with the script pattern in git history (import the real `js/math/*.js` functions, run them over representative inputs including the documented boundary cases, write the JSON) if you change a formula. `python/tests/` also covers `python/fuel_pipeline/`'s pure cleaning/filtering logic (`clean.py`). `fetch.py`/`publish.py` do real network I/O and are deliberately not unit tested, the same distinction as GPS/DOM/network below. Everything outside `js/math/` and `python/fuel_pipeline/clean.py` (GPS, DOM, network, Supabase, `localStorage`) is still untested beyond syntax-checking and manual/Playwright verification; see the module structure note under Architecture for why those pieces can't be unit-tested the same way. CI (`.github/workflows/tests.yml`) runs both suites on every push/PR.
- **Weekly fuel-economy data refresh**: `.github/workflows/weekly-fuel-data-refresh.yml` runs `python -m fuel_pipeline` (from `python/`) on a Wednesday cron, fetching fueleconomy.gov's bulk CSV, cleaning/filtering it (`python/fuel_pipeline/clean.py`), and upserting it into the `vehicle_fuel_economy` Supabase table via the `supabase` Python package and a service-role key (`SUPABASE_SERVICE_ROLE_KEY`/`SUPABASE_URL` repo secrets, which must be added manually under Settings → Secrets and variables → Actions, never typed into a shell command in a session transcript, same rule as the Supabase CLI token/password above). It's not committed to the repo; the app's Settings vehicle picker (`js/ui/vehiclePicker.js`) reads the table live via the existing Supabase client. Trigger it manually via the Actions tab (`workflow_dispatch`) to verify setup without waiting for the schedule.
- **Verify UI changes with a real screenshot**: this is a visual/mobile-layout-heavy app, and CSS that looks right in source can render wrong (see the `@media (orientation: landscape)` history). Don't just read the CSS — run a local server (`python3 -m http.server`) and drive it headlessly (e.g. Playwright, installed ad hoc into the scratch dir since it isn't a project dependency) to screenshot both portrait and landscape before calling a layout change done.
- **Test without driving**: tap the "Dev tools ▸" disclosure link under the trip controls (collapsed by default as of 2026-07-16 so it doesn't clutter the live view — no query param needed), then pick a profile (Full range, Residential, Inner City, Highway, Rural — `SIMULATED_DRIVE_PROFILES` in `js/app.js`) from the dropdown next to "Start Simulated Drive" to feed synthetic speed data through the exact same `handlePosition()` pipeline real GPS uses — exercises speed/pace/gauges/trip-recording end to end without leaving the couch. An optional "sim. speed limit mph" input next to the profile dropdown (`#simulate-speed-limit`, 2026-07-25) sets `devSpeedLimitOverrideMph` and skips the real Overpass lookup entirely, so the speed-limit-gated "limit" zone state and the reframed trip summary can be exercised without a real drive or network access — see the zone indicator entry below. Must be removed before shipping to real study participants — see Pre-launch checklist below.
- **Database schema changes**: use versioned migrations via the Supabase CLI (`brew install supabase/tap/supabase`), not the old single-file `supabase/schema.sql` (deprecated, kept only for history). Workflow: `supabase migration new <description>` creates a timestamped file in `supabase/migrations/`; write the SQL there (additive changes as idempotent `alter table ... add column if not exists`, same reasoning as before — the live table already exists and won't be recreated); then `supabase db push` applies any pending migrations to the linked remote project. The CLI must be linked once per machine (`supabase login --token ...`, then `supabase link --project-ref ojhhlxmbawckknnpgmfj`) — see git history around 2026-07-14 for how that was set up if it needs redoing. `supabase db push` needs the database password (Supabase dashboard → Connect → Direct → password, or reset it there) passed via `-p`; it does NOT need Docker. (`supabase db pull`/`db dump` do need Docker for the shadow-database/pg_dump-version-matching machinery — avoid those; if you ever need a raw schema dump instead, `brew install postgresql@17` and use `pg_dump` directly against the session pooler host, since the direct-connection hostname is IPv6-only and this network doesn't resolve it.) Migration history is tracked in a remote table the CLI manages — `supabase migration list -p <password>` shows what's applied. Never type a Supabase access token or DB password directly into a shell command visible in a Claude Code session transcript (`! command`); write it to a local file outside the repo first (outside the `!` proxy, in a real terminal window) and read it via command substitution instead, e.g. `-p "$(cat ~/.some_token_file)"`.

## Architecture

**No framework, no bundler.** `index.html` loads a single entry point, `js/auth.js`, via `<script type="module">`; everything else is pulled in through ES module imports (including the Supabase client from `esm.sh`, a CDN that serves npm packages as ES modules — used instead of a local `node_modules` install since there's no build step).

**Module structure (2026-07-31 restructuring)**: `js/app.js` was originally one ~1360-line file holding every concern (GPS, speed-limit lookup, zone/pace math, trip recording, DOM rendering, audio/haptics, settings, the dev-only simulated-drive tool) as module-scope functions and shared `let`s. It's now split into one class/module per concern, each owning the state it used to share implicitly, with `js/app.js` reduced to a composition root that instantiates and wires them together:
- `js/math/` — pure functions and constants only (`paceMath.js`, `zoneState.js`, `geoMath.js`, `speedLimitParsing.js`). No DOM, no `fetch`, no `localStorage`. This is the set mirrored in `python/paceometer_math/` for testing (see Commands above) — if you're looking for `nextZoneState`, `marginalSecondsSaved`, `zoneCeilingMph`, `haversineMeters`, `parseMaxspeedTag`, etc., they live here now, not in `app.js`.
- `js/gps/geolocationTracker.js` — `GeolocationTracker` class: `watchPosition`/`clearWatch`, the Screen Wake Lock trio, and `deriveSpeedMph()` (the `coords.speed`-or-Haversine-fallback logic, shared by real GPS and the simulated-drive tool).
- `js/speedLimit/speedLimitService.js` — `SpeedLimitService` class: the Overpass lookup/mirrors/retry/cache/throttling, plus the dev-override hook the simulated-drive tool uses.
- `js/trip/trip.js` + `tripsApi.js` — `Trip` class (start/recordSample/finish, all the accumulator fields) and the isolated Supabase write.
- `js/ui/dashboardView.js` + `settingsControls.js` — `DashboardView` class (every DOM ref and DOM-writing function) and `SegmentedSetting`, one reusable class replacing what used to be three near-identical Appearance/Zone-Sensitivity/Sound blocks.
- `js/feedback/audioFeedback.js` — `AudioFeedback` class: the Web Audio tones and haptic patterns.
- `js/dev/simulatedDrive.js` — the entire dev-only simulated-drive tool, deliberately self-contained (owns its own DOM refs) — see the Pre-launch checklist below, now just "delete this file + its one import line in `app.js` + its HTML block."

This was a structural-only refactor — every formula, threshold, and piece of wording below is unchanged; only *where* the code lives moved. The historical narrative below still cites `js/app.js` by habit in places (e.g. "`setZoneDisplay` in `js/app.js`") for pieces that have since moved into one of the modules above — if a cited function name isn't in `app.js` anymore, check the module map first before assuming it was removed.

**Module graph**: `auth.js` (entry) → imports `supabaseClient.js` (client init) and `app.js` (the composition root, still exports exactly `startApp`/`stopApp`/`setViewportZoomEnabled` — `auth.js` itself needed zero changes for the 2026-07-31 restructuring). `app.js` in turn imports every module listed above.

**Architecture diagrams** (`docs/diagrams/`, added 2026-07-31): a package/dependency diagram, a class diagram, a sequence diagram (one GPS fix flowing through the modules above), and an activity diagram for `nextZoneState`'s own branching logic — all real UML via PlantUML (`.puml` sources checked in alongside the rendered `.pdf`s), not the mermaid approximation. Regenerating after an edit needs `brew install plantuml graphviz` (Graphviz gives PlantUML's layout engine much cleaner output than its built-in one), then `plantuml -tpdf <name>.puml` from that directory.

**Screen-gating pattern**: `index.html` has three top-level `.screen` divs — `#auth-screen`, `#app`, and `#settings-screen` (added 2026-07-16) — toggled via the `.hidden` class. `auth.js`'s `supabase.auth.onAuthStateChange` listener is the single source of truth for the *signed-in vs. signed-out* split — it calls `startApp()` (begins `watchPosition`) and shows `#app` when a session exists, and calls `stopApp()` (clears the GPS watch, resets trip state) and shows `#auth-screen` when it doesn't; both `showApp()`/`showAuth()` also force `#settings-screen` hidden so it can never stay visible across a sign-out. Don't add a second place that shows/hides `#auth-screen`/`#app`; route all auth-driven visibility changes through that listener. The `#app` ↔ `#settings-screen` toggle is intentionally a *separate*, independent mechanism (`settings-nav`/`settings-back` listeners in `js/app.js`) — the driver stays signed in the whole time, so it doesn't belong in the auth listener, same reasoning as the trip-summary inline swap below.

**Screen wake lock (2026-07-27)**: real-drive testing surfaced that the phone would fall asleep mid-drive like any other web page, forcing the driver to keep tapping it awake — the opposite of an instrument meant to be glanced at. `requestWakeLock()`/`releaseWakeLock()` in `js/app.js` wrap the Screen Wake Lock API (`navigator.wakeLock.request("screen")`) and are called from `startApp()`/`stopApp()` — i.e. tied to the tracking session (signed-in + `#app` visible), the same lifecycle boundary `watchId` uses, not to which sub-screen (settings vs. live dashboard) is showing. The OS releases the lock automatically whenever the tab/PWA is backgrounded (app switch, real screen lock), so a `visibilitychange` listener re-requests it when the page becomes visible again while a watch is still active, or a brief backgrounding would otherwise lose the lock for the rest of the drive. Supported on iOS Safari 16.4+ and Chrome/Android, including standalone PWA mode; the request silently no-ops (falls back to the OS's normal timeout) on unsupported browsers or if the request itself fails (e.g. low battery on some platforms) — not yet verified against an actual drive, only smoke-tested that the app still loads.

**Speed → pace pipeline** (`js/app.js`): `handlePosition` prefers `coords.speed` from the Geolocation API; when that's `null` (no GPS chip — true of every desktop browser, and occasionally a phone's first fix), it falls back to a Haversine distance/time delta between consecutive fixes. Either way, the *only* output that leaves `handlePosition` is a plain `mph` number — raw lat/lng from `lastPosition` is used transiently for the fallback calc and never stored or transmitted. Pace is computed live from that same `mph` value using `t = d/v` (Peer & Gamliel 2013, Formula 1: minutes to cover a fixed 10-mile reference distance) — this is the one formula in the codebase that's directly literature-validated; if you change the reference distance or the formula shape, that traceability is lost, so check the sibling lit-review repo first (see "What this is" above).

**GPS fallback noise guards, and a known-open gap** (`js/app.js`, `MAX_FIX_ACCURACY_METERS`/`MAX_PLAUSIBLE_MPH` in `handlePosition`): desktop Wi-Fi/IP-based positioning is coarse and jumps between fixes, so the Haversine fallback above can turn ordinary position noise into a large apparent speed. Two guards catch the extreme case: a fix isn't remembered as "last known position" for the delta calc unless its reported `coords.accuracy` is within 100m, and any resulting speed above 200mph is discarded outright rather than shown/recorded (2026-07-15, added after "huge numbers on refresh" during dev-server testing). **Not fully fixed**: two fixes can still differ by tens of meters from ordinary noise even while both individually pass the 100m accuracy gate — e.g. a stationary laptop can still show a spurious few-mph or double-digit reading. The real fix (not yet implemented, see `TODO.md`) is to only trust a delta as real movement when the apparent displacement exceeds the *combined* accuracy radius of the two fixes, not just each fix's individual accuracy. Much smaller-magnitude on a real phone (GPS accuracy ~5-10m vs. desktop's hundreds), but not zero risk there either — don't assume this is a dev-only artifact.

**Core Function/Core Loop: the zone indicator** (`js/app.js`): the app's build follows a 5-stage MVP funnel from `research_plan.qmd` (`@sec-mvp-funnel`) — Core Function, Core Loop, Accessory Features, Surface Area Check, Retention Hook — each stage gating what gets built next. `marginalSecondsSaved(mph)` answers the Core Function question directly: at the current speed, would going `ZONE_SPEED_INCREMENT_MPH` (+10mph) faster still save `ZONE_THRESHOLD_SECONDS` or more over the `PACE_REFERENCE_MILES` reference distance? That's the exact hyperbola argument from `paceometer_review.qmd`'s own illustrative tool, checkable against its worked examples. The live indicator is a 4-state traffic light (`nextZoneState`/`ZONE_STATE_LABELS`/`setZoneDisplay` in `js/app.js`; `.zone-indicator.green/.yellow/.red/.limit` in `css/style.css`) — green/yellow/red purely from the time-math above, plus a 4th `"limit"` state (violet, distinct from all three) that overrides everything else once a known posted speed limit is reached, see the speed-limit-lookup entry below. Each state shows a big word, a big color-matched number, and a caption — never a sentence to parse; current draft labels (pending a comprehension-check pass, same process used for the end-of-trip wording below) are `TIME ADDS UP HERE` / `GAINS ARE SHRINKING` / `NO TIME LEFT TO GAIN` / `AT THE SPEED LIMIT`.

`ZONE_THRESHOLD_SECONDS` (red/not-red line) and `ZONE_NEARING_THRESHOLD_SECONDS` (yellow/green split, always exactly double the first, same clean-hyperbola-number coincidence as before) are **driver-adjustable as of 2026-07-25** — no longer fixed constants, but `let` bindings set from `ZONE_THRESHOLD_PRESETS` (`standard`/`strict`/`strictest`, 90s/150s/240s) via Settings → Zone Sensitivity, `localStorage`-backed the same way `APPEARANCE_STORAGE_KEY` works. `standard` (90s, ~58.4mph ceiling) is the new default per Helveston's guidance that the original 60s default ("~73mph, ordinary highway cruising still reads as still helps") wasn't asking for enough of a time payoff. None of the three presets' specific values are literature-derived. `pct_time_in_zone` is still computed off the red/not-red line (now whichever preset is active), and now explicitly excludes `"limit"` samples from the "in zone" side of the ratio (grouped with red) — a judgment call made when the gating was added, not something explicitly specified beforehand, worth revisiting if you want that metric to reflect pure time-math regardless of gating.

`ZONE_HYSTERESIS_SECONDS` (±5s dead-zone, applied independently at both time-math boundaries) prevents flickering when GPS noise puts the driver right at a boundary, and a brief `zone-flash` animation marks the moment the state actually changes (Core Loop's "display confirms the new state"). `SPEED_LIMIT_HYSTERESIS_MPH` (±2mph) does the same job at the `"limit"` boundary.

**Speed-limit lookup and full gating (2026-07-25)**: the zone was previously defined only against the fixed time-savings hyperbola, not the posted speed limit — deliberately, since "speed-limit lookups have no free tier" (confirmed with the professor's collaborator, 2026-07-15). That reasoning no longer holds: `handlePosition` now calls `maybeQuerySpeedLimit(coords, timestamp)` (fire-and-forget, not awaited) which queries OpenStreetMap's free public Overpass API (`SPEED_LIMIT_API_URL`, nearest tagged way within `SPEED_LIMIT_QUERY_RADIUS_METERS`) for a `maxspeed` tag, throttled by **both** distance (`SPEED_LIMIT_QUERY_MIN_DISTANCE_METERS`) and time (`SPEED_LIMIT_QUERY_MIN_INTERVAL_MS`) since the last query, so an ordinary drive doesn't hammer a free public API. Any failure (network error, timeout, no coverage, unparseable `maxspeed` value) resolves `knownSpeedLimitMph` to `null` rather than reusing a stale value — a real fetch failure means the app genuinely doesn't know anymore. `nextZoneState` checks this before the ordinary red/yellow/green math and can override it entirely: once at/above a known limit, the app never suggests "still helps," full stop, regardless of what the pure time-savings math would say (e.g. a school zone below the zone-ceiling speed). This is an **explicit, discussed exception** to the privacy invariant below — the driver's current lat/lng is sent transiently to Overpass on each throttled lookup, never stored, never sent to Supabase, never logged — not something to silently extend to other third-party lookups without the same conversation. Confirmed via a direct browser fetch test that Overpass has no CORS restriction, but real-world coverage/accuracy/latency of the public instance hasn't been verified against an actual drive.

**Two real bugs found and fixed in the 2026-07-25 speed-limit-gating work (fixed 2026-07-26)**, both discovered by dogfooding rather than code review alone:
1. `timeSavedBySpeedingSeconds`/`timeSavedBySpeedingSoFar` had the subtraction backwards — `limitTrackedSeconds − idealSecondsAtLimit` instead of `idealSecondsAtLimit − limitTrackedSeconds`. Since driving faster than the limit makes `limitTrackedSeconds` *smaller* than `idealSecondsAtLimit`, the old formula went negative and got `Math.max(0, …)`-clamped to a flat `0s` on every trip that actually sped, regardless of how much. Caught by the user running a real simulated drive with a low sim speed limit and getting a suspicious `0s`.
2. `nextZoneState` could get permanently stuck in `"limit"`: if `knownSpeedLimitMph` reverted to `null` (Overpass timeout, rate-limit, or leaving mapped coverage) while the *previous* zone state was `"limit"`, none of the function's transition branches matched a `previous` of `"limit"` once the limit itself was unknown again, so the display (and `pct_time_in_zone` accumulation) froze on `"AT THE SPEED LIMIT"` for the rest of the trip. Fixed by resetting `previous` to `null` at the top of `nextZoneState` whenever `previous === "limit" && knownSpeedLimitMph === null`, before the rest of the gating logic runs. Confirmed via an isolated re-implementation-free test (copy the exact function into a throwaway `.mjs` and drive it with scripted inputs — the same technique to reach for when `document`-coupled module code can't be imported directly in Node) and, unplanned, live in the browser: a real Overpass 503 fired mid-test from repeated querying and the app recovered correctly instead of freezing.

Also surfaced by an end-to-end test against real OSM data (not the simulated-drive override): the Overpass query's `around:30` radius doesn't check the fix's `coords.accuracy` at all (unlike `MAX_FIX_ACCURACY_METERS` elsewhere in this same function), and picks whichever tagged way Overpass returns first within that radius, not necessarily the geometrically nearest one — both are real accuracy risks worth knowing about before trusting the "limit" state on an actual drive, not yet fixed. Separately, the free public Overpass instance visibly rate-limits (`503`) under a burst of queries in a short window — expect that in real-world use, not just heavy testing.

**Speed-limit lookup resilience: mirrors, wide-radius retry, confirmed-reading cache (2026-07-27)**: real-drive testing (first drive with this feature live) confirmed the lookup is accurate whenever it has coverage, but coverage itself is spotty — expected, since it's a direct function of OSM's `maxspeed` tagging completeness and no client-side change adds tags that don't exist. Three additions narrow the gap without ever inventing a number OSM doesn't have, all in the same speed-limit block in `js/app.js`: (1) `SPEED_LIMIT_API_URLS` is now an array of three public Overpass mirrors (`overpass-api.de`, `overpass.kumi.systems`, `overpass.openstreetmap.fr`); `queryOverpass()` tries them in order and moves on from a non-ok response or a network/timeout error rather than failing the whole lookup — addresses the rate-limiting/`503` issue noted just above. (2) `fetchSpeedLimitMph()` retries once at `SPEED_LIMIT_QUERY_RADIUS_WIDE_METERS` (100m, up from the base 30m) if the tight radius comes back empty across every mirror, since some "no result" cases are a tagged way sitting just past the original radius. (3) `speedLimitCache` remembers each *confirmed* (real OSM tag, never inferred) reading for `SPEED_LIMIT_CACHE_MAX_AGE_MS` (5 min) within `SPEED_LIMIT_CACHE_RADIUS_METERS` (120m); `maybeQuerySpeedLimit()` falls back to `cachedSpeedLimitNear()` when a fresh lookup comes back empty, so a brief gap between successful lookups — or re-driving an already-queried stretch — doesn't blank the sign even though nothing about the road changed. The cache is in-memory only, per session, same as `lastSpeedLimitQuery` already was — no new persistence, no change to the privacy invariant below. None of this has been verified on an actual drive yet (only syntax-checked and smoke-tested that the app still loads) — a paid speed-limit API remains the only real fix for coverage itself, noted as a known limitation until that's in budget.

**Always-on speed limit sign (2026-07-26)**: `#speed-limit-sign`/`#speed-limit-sign-value` in `index.html`, `setSpeedLimitSignDisplay()` in `js/app.js`, called from `handlePosition` every fix. A permanent corner-anchored HUD element (top-right, mirroring `.settings-nav`'s top-left placement/margin) showing whatever `knownSpeedLimitMph` currently is — the same value the zone-gating logic already tracks, just surfaced directly instead of only implied by the `"limit"` zone state. Styled as a literal white/red/black road sign (`.speed-limit-sign`/`.speed-limit-sign-value` in `css/style.css`) and **deliberately not theme-colored** — a real sign doesn't change appearance in dark mode, and staying visually literal is what makes it instantly readable at a glance. Hidden entirely (not a `"--"` placeholder) whenever no limit is known. This is a real feature under consideration for shipping, not a dev tool — unlike the simulated-drive block, it does not appear on the pre-launch removal checklist below.

**Sound setting (2026-07-26)**: Settings → Sound (`#sound-switch`, `SOUND_STORAGE_KEY = "paceometer-sound"`, same `localStorage` pattern as Appearance/Zone Sensitivity). Gates at the shared `playTone()` function in `js/app.js` — a single `soundMuted` check there silences the zone-change chime and both trip start/end tones uniformly, since everything audio-related already routes through that one function. Deliberately does **not** touch `playZoneChangeHaptic()` — the point is avoiding a clash with music/calls, not suppressing feedback altogether for a driver who relies on the buzz.

**Wording standing rule (2026-07-26)**: beyond the existing "confirm actual comprehension, don't ship a single best-guess rewrite" standard (see the wording-revision history above), any copy touching time-saved-by-speeding, speed itself, or the zone/limit state must also pass a second check: *could a driver read this as encouragement to go faster?* The live in-trip line and the end-of-trip headline both used to read as a scoreboard the driver could feel invited to make go up ("Xs faster than the speed limit") — fixed by prefixing both with "only" (`setTripZoneProgressDisplay`/`showTripSummary` in `js/app.js`; the end-of-trip version is a smaller `.trip-summary-value-prefix` span, not jammed into the 5rem number itself, so it reads as a qualifier rather than part of the number). Correctness of the underlying math does not excuse framing that cuts against the project's reduce-speeding goal — default to language that undersells the gain ("only", "just", "barely") rather than neutral or celebratory phrasing.

**Trip recording is a separate layer on top of the live display**: `recordSample()` only accumulates into `trip` while `recording` is true, i.e. between Start Trip and End Trip taps. The live speed/pace/zone readout runs continuously once signed in regardless of whether a trip is being recorded. `endTrip()` sends the aggregates to Supabase — `avg_speed_mph`/`max_speed_mph`/`min_speed_mph`, `sample_count`, `distance_miles` (integrated from `mph × Δt` between samples, not from lat/lng, so it doesn't violate the privacy invariant below), `avg_pace_seconds` (a genuinely separate running mean of per-sample pace, not derived from `avg_speed_mph` — mean-of-pace ≠ pace-of-mean-speed, so comparing the two after a drive is a sanity check on the pace formula itself), `pct_time_in_zone` (Accessory Feature — the same hysteresis-corrected `zoneState` the live indicator computes, time-integrated over the trip; time below `PACE_MIN_SPEED_MPH` is excluded from both sides of the ratio rather than counted as "out of zone"), and `pct_time_under_limit` (2026-07-25, same exclusion principle but keyed off whether a speed limit was known for that sample — see `trip.limitTrackedSeconds`/`underLimitSeconds` in `recordSample`). Not yet surfaced in any UI (a future trip-history tab is the plan) but populating now. Never a location trace, beyond the transient Overpass lookup described above.

**End-of-trip summary** (`js/app.js`, `showTripSummary`/`hideTripSummary`/`endTrip`/`zoneCeilingMph`; `index.html`, `#trip-summary`): the Accessory Feature stage's "kept only if it reinforces the core loop" gate is why this is deliberately just the one number, no historical trends, nothing about the car. It's an inline swap: ending a trip hides `#readout`/`#trip-controls` and shows `#trip-summary` in their place — **explicitly kept as an inline swap, not a separate screen, during the Surface Area Check discussion (2026-07-16)**, since the plan counts "screens" as UX concepts rather than literal routes and there was no functional reason to change it. The live in-trip readout (`setTripZoneProgressDisplay`, `#trip-zone-progress`) was originally a "Trip: ±X vs 55mph" baseline-speed comparison that predated and contradicted this summary's zone framing — resolved 2026-07-15 by replacing it with a running "% of trip in zone so far" readout, later the same day joined by a second line (`#trip-zone-progress-time`) showing the running version of the seconds-behind-pace number described below. **Wording resolved 2026-07-16**: both that second line and the end-of-trip caption (`tripSummaryCaptionEl`) had used "behind the fastest pace," flagged as confusing ("fastest pace" reads as literal top speed; "behind" doesn't say behind what). Out of 4 drafted candidates, the user picked the zone+reference-speed hybrid: both now read "Xs behind the ~73mph efficient pace[, so far]," with the `~73` computed live as `Math.round(zoneCeilingMph())`, never hardcoded.

**The end-of-trip headline number itself was revised again later the same day (2026-07-15):** it originally showed that same "% of trip in zone" as a flat percentage ("X% of this trip, more speed would have helped"). Dogfooding a simulated highway drive (65-80mph, i.e. cruising right at/above the ~73mph zone ceiling) showed the problem: that trip reported 100%, which reads as "you should have gone even faster than 80mph" — exactly backwards from the app's point, and it doesn't distinguish a trip that was 6 seconds off an efficient pace from one that drove 25mph the whole time. Replaced with a concrete seconds value: `secondsBehindPace = inZoneSeconds − (inZoneMiles / zoneCeilingMph()) × 3600`, clamped to ≥0 — actual time spent, only during the portion of the trip where the zone state was green/yellow (not red), above what those same miles would have taken at the exact zone-ceiling speed (`zoneCeilingMph()`, solved algebraically from `ZONE_THRESHOLD_SECONDS`, not hardcoded). A highway-speed trip now reports a small number; a trip driven well under an efficient pace reports a larger one. `pct_time_in_zone` is unchanged and still saved to Supabase (useful for research analysis) — only the on-screen headline number changed. Full derivation and the literature-grounding question (none of these thresholds are literature-derived; only `t=d/v` itself is) are written out in README.md's "How the pace/zone math works" section for a non-AI reader.

**Reframed again 2026-07-25**: `secondsBehindPace` (vs. the fixed `zoneCeilingMph()` hyperbola) still read as faulting the driver for not speeding more — it framed a small number as "you barely fell short of an efficient pace," when the actual goal is fewer people speeding at all. Replaced with `timeSavedBySpeedingSeconds` in `endTrip`: `limitTrackedSeconds − idealSecondsAtLimit` (clamped ≥0), computed per-sample against the *real* posted speed limit (`trip.idealSecondsAtLimit` accumulates `(mph/knownSpeedLimitMph) × seconds` in `recordSample`) rather than the fixed zone ceiling. Caption is now "faster than if you'd strictly followed the speed limit" — a small number is the honest success case (speeding barely gained anything), not a shameful one. Only meaningful where a speed limit was known for at least part of the trip; falls back to "no speed limit data this trip" otherwise (always true for the simulated-drive dev tool unless its speed-limit override is set, since real fixes at `(0,0)` never match a road). The live in-trip second line (`setTripZoneProgressDisplay`/`#trip-zone-progress-time`) was reframed the same way in the same pass, so the running number and the end-of-trip number stay the same metric at two points in time.

**Settings screen** (`js/app.js`, `settings-nav`/`settings-back` listeners; `index.html`, `#settings-screen`; `css/style.css`, `.settings-*`): built 2026-07-16 as part of Surface Area Check, reachable via a gear icon (44×44px tap target — an earlier ~12×21px version was reported as both hard to tap and rendering flush against the viewport edge because `env(safe-area-inset-top, 16px)` resolves to a *defined* `0` on non-notch screens, so the fallback never applied; fixed with `max(env(...), 16px)`) on the live dashboard. Contains an "About Paceometer" section (plain-language pace formula, color-indicator meaning, end-of-trip number — updated 2026-07-25 to describe the adjustable threshold and the speed-limit gating, no longer claims the app "doesn't know the speed limit"), a "Privacy" section (updated 2026-07-25 to disclose the transient Overpass lookup — see privacy invariant below — plus what summary fields are saved, RLS scope), and a "Zone Sensitivity" section (2026-07-25, `#zone-threshold-switch`, three presets) — all held to the same literature-backed-vs-design-choice honesty standard as this file and README.md, just in plainer language for a non-technical driver. Sign-out moved here from its old floating position directly on `#app`. The segmented-control CSS (`.segmented-control`/`.segmented-option`, renamed from `.appearance-switch`/`.appearance-option` on 2026-07-25 when Zone Sensitivity started reusing the same pattern) is shared between Appearance and Zone Sensitivity — element IDs (`#appearance-switch`, `#zone-threshold-switch`) stay specific, only the CSS classes are generic.

**Fuel-cost trip summary (2026-08-03)**: extends the existing time-saved-by-speeding number with a second, complementary one: roughly what the trip cost in gas, and roughly how much of that came from driving over the speed limit. `js/ui/vehiclePicker.js`'s `VehiclePicker` class is a cascading Make → Model → Year → Variant picker in the Settings screen. There's no separate "trim" column in fueleconomy.gov's data, so "Variant" is built from whichever of `trany`/`drive`/`displ`/`cylinders` distinguishes rows sharing the same make/model/year. It's backed by the `vehicle_fuel_economy` Supabase table and resolves to a single `{ cityMpg, highwayMpg, label }` object cached in `localStorage` (`paceometer-vehicle`), resolved once and used directly, the same style as `ZONE_THRESHOLD_PRESETS`. A plain editable `paceometer-gas-price` setting (default verified against AAA's national average on 2026-08-03, not a claim about the driver's actual local price) converts gallons to dollars in `app.js`, keeping `DashboardView` a "dumb" renderer of already-converted numbers.

`js/math/fuelMath.js`'s `gallonsPerMile(mph, cityMpg, highwayMpg)` is the only new formula, mirrored in `python/paceometer_math/fuel_math.py` and golden-vector-tested (`tests/golden_vectors/fuel_math.json`) exactly like the pace/zone math. The dataset only gives two real data points per vehicle: EPA city (21.2mph test average) and highway (48.3mph test average) MPG, both confirmed directly against fueleconomy.gov's own test-schedule page. So there's no true speed-swept curve to draw from. Between the two anchors, gallons/mile is a straight line (a reasonable interpolant, though the lit review's Wang et al. 2008 finds the real minimum sits around 31-43mph, inside this range). **Above the highway anchor, where most real speeding-over-the-limit driving happens, a straight line through just the two anchors keeps improving mileage as speed rises.** That's backwards, and it would have told a driver they saved gas by speeding in the most common real case. Found and fixed the same session it was specced, caught before shipping, not after. Fixed by growing gallons/mile quadratically above that anchor. The v² *shape* is ordinary aerodynamics (drag force ∝ v², power to overcome it ∝ v³, so fuel/mile from drag alone ∝ v²; see `paceometer_lit_review/lit_review.md` section 3), but the specific *coefficient* is only calibrated from a widely-cited rule of thumb (about 10% more fuel at 110 vs. 100 km/h) that the lit review itself flags as needing primary-source verification before academic citation. It's solved algebraically in code, not hardcoded, the same way `zoneCeilingMph` is, so it's easy to replace once a tighter primary-sourced fit (Greene 1981, Wang et al. 2008) is worth the effort. Treat the magnitude as same-ballpark, not exact, until then.

`js/trip/trip.js`'s `Trip` class mirrors its own existing `limitTrackedSeconds`/`idealSecondsAtLimit` pattern for fuel: `actualGallons` covers the whole vehicle-tracked trip (the "what did this cost" number), while `limitTrackedGallons`/`idealGallonsAtLimit` are restricted to samples where a speed limit was *also* known, so the "gas saved by speeding" comparison is apples-to-apples. `gallonsSavedBySpeeding` is clamped at 0 for the same reason `timeSavedBySpeedingSeconds` is: the model isn't strictly monotonic in speed (city-to-highway driving genuinely improves mileage here, matching real EPA data), so a trip driven entirely at or under the limit could otherwise show a small negative "savings," which would read as encouraging speeding and violate the wording standing rule above. The two new trip-summary lines (`DashboardView.showTripSummary`, `#trip-summary-gas-cost`/`#trip-summary-gas-saved`) are **draft copy, not yet wording-reviewed**. They need to go through the same comprehension-check plus never-reads-as-encouraging-speeding process as the rest of the trip-summary copy before shipping (see `docs/TODO.md`).

The `vehicle_fuel_economy` table (`supabase/migrations/20260803183109_...sql`) is the **first table in this schema that isn't per-user**. It's shared reference data, RLS-enabled with a single `select`-for-`authenticated`-`using (true)` policy and no insert/update/delete policy for that role at all, since only the weekly refresh Action (via a service-role key, which bypasses RLS) ever writes to it. Don't copy the `trips` table's `auth.uid() = user_id` pattern here; there's no `user_id` column and there shouldn't be one. `trips` itself gained `gallons_used`/`gallons_saved_by_speeding`/`vehicle_label` (`supabase/migrations/20260803183130_...sql`). `vehicle_label` is a plain text snapshot, not a foreign key, so a past trip's summary stays meaningful even if that exact vehicle row changes in a later refresh or the driver switches cars.

**Bug found running the pipeline for real the same day**: the first version of the table's migration only granted `select` to `authenticated`, so the weekly refresh script's first live run failed with `permission denied for table vehicle_fuel_economy` even though the service-role key itself was valid. `service_role` bypasses RLS, but bypassing RLS and holding an ordinary table-level `GRANT` are separate things in Postgres; RLS bypass alone doesn't imply `SELECT`/`INSERT`/`UPDATE` privileges. Fixed in a follow-up migration (`supabase/migrations/20260803193402_grant_service_role_on_vehicle_fuel_economy.sql`): `grant select, insert, update on public.vehicle_fuel_economy to service_role;`. This is the second time the "Automatically expose new tables is off" trap (see the Supabase access model entry below) has bitten this project, and the first time it's shown up per-role rather than per-table: a new table needs the grant repeated for every role that touches it, not just once.

**Portrait/landscape layout**: the app is meant to be mounted either way on a dash, so `css/style.css` gives landscape its own explicit font sizes/spacing in `@media (orientation: landscape)` rather than reusing the portrait `vw`-based formula scaled down — they looked comparable on paper but wildly different on an actual phone, which is why real screenshots (see Commands) matter here more than for most CSS changes. `index.html` also carries a small inline script working around a known iOS Safari bug where the layout viewport fails to recompute after rotation (nudges `initial-scale` off 1 and back on `orientationchange`).

**Visual identity: GWU colors, monospace, light/dark appearance (settled 2026-07-22)**: `css/style.css`'s `:root` token block (`--accent`/`--accent-2`/`--surface`/`--font-body`/`--font-numeric`, introduced 2026-07-21 to move off a flat-black/pure-white/default-system-sans look) went through several exploratory dev-tool comparison passes — theme and font pickers (peaking at 18 palettes × 27 fonts), a 0-5 color-intensity dial, and a six-mode neon/pastel/metallic/glass/retro texture axis, each a `<select>` behind the dashboard's "Dev tools ▸" disclosure setting a `data-*` attribute the CSS keyed off of. **All of that dropdown machinery has since been fully deleted** — every one was resolved to a single permanent choice and its comparison UI/CSS/JS removed; if you see `data-theme`/`data-font`/`data-color-level`/`data-mode` selects mentioned in git history, none of it exists in the current codebase. Final state: **GWU's official colors** (`--accent` #0096d6 Colonial blue, `--accent-2` #a99768 buff/tan — Professor Helveston's institution) and **system monospace** (`ui-monospace`/SF Mono), chosen from a Playwright-screenshotted bake-off (two labeled contact-sheet PNGs kept in `dev-assets/` at the user's request); **color level 5** (the strongest intensity option), folded permanently into `--extra-tint`/`--extra-tint-dim`/`--border-eff`/`--button-bg-eff`; and, replacing the six-mode texture axis, a real **light/dark appearance** feature (not a dev tool) defaulting to `@media (prefers-color-scheme)` with an explicit override via Settings → Appearance (`js/app.js`, `APPEARANCE_STORAGE_KEY`), which reuses the now-free `data-theme` attribute for `:root[data-theme="light"|"dark"]`.

Two gotchas worth knowing if you touch appearance-related CSS: (1) the `@media (prefers-color-scheme: light)` block's plain selectors (`body`, `.zone-indicator.*`, etc.) have the *same* specificity as base rules setting those properties elsewhere in the file, so it must stay physically *after* them in `css/style.css` (it's kept at the very end) to win on source order — an attribute-scoped `:root[data-theme=...]` selector doesn't have this problem, since it outranks a plain `:root` on specificity regardless of position, but the plain `@media` block does; moving it back up silently breaks system-light detection. (2) Any per-appearance token that's a `color-mix()` formula referencing `--text-secondary`/`--text-primary` (like `--extra-tint`) recomputes differently in light vs. dark since those change — a formula validated in one appearance isn't automatically safe in the other; see the accessibility entry below for a real bug this caused.

**Audio feedback (2026-07-22)**: Web Audio API oscillator tones, no audio files, zero network dependency — a zone-state-change chime (pitched by valence: green rings higher than red) alongside the existing `zone-flash` animation, and a two-note trip start/end tone. Deliberately scoped to reinforcing signals already on screen, not new coaching content — spoken pace/zone feedback was raised as a bigger step (closer to active coaching, same IRB-disclosure category as the Retention Hook) and logged in `TODO.md` instead of built. `AudioContext` is created lazily on the first tap anywhere on the page since autoplay policies block audio before a user gesture.

**Accessibility (2026-07-22)**: a manual audit against WCAG POUR, the Android accessibility guide, an MDN mobile checklist, and a general 5-step checklist (contrast ratios computed from real hex/rgba values, not eyeballed), followed by an automated pass (Lighthouse + axe-core) and four explicit user decisions. Both tools now score clean (Lighthouse 100/100 accessibility; axe 0 violations except one deliberately-skipped item, below). Full report was given inline in that session's chat, not saved to a file. Fixes, all in `css/style.css` unless noted:
- **Light-mode contrast** — the zone-indicator traffic-light text, `.status`/`.status.live`, `.pace`, `.zone-caption`, and the settings-section headings/body text were all tuned only against a dark background and silently failed WCAG's 4.5:1 (some as low as 1.28:1) once light mode became real; each now has a light-mode-specific override, with dark mode's originals explicitly restated in `:root[data-theme="dark"]`. The automated axe pass caught several of these (the raw-hex ones) that the manual review missed — Lighthouse's single page load never sees past the initial auth screen, and a manual review doesn't naturally re-measure every token-based color per appearance.
- **Button text** — `--accent-text` changed from white to a dark navy (`#0a2338`) since white failed 4.5:1 against both ends of the `--accent`→`--accent-2` button gradient; the one place the button isn't literally the GWU colors as supplied — `--accent`/`--accent-2` themselves are untouched.
- **`aria-live`** — a zone-state-change announcer (`#zone-state-announcer`, updates only on an actual state change, not every GPS sample), `polite` on trip-summary save status, `assertive` on the auth error.
- Real `<label>`s on the auth inputs (new `.sr-only` utility class); `.segmented-option`/`.link-btn` touch targets bumped to `min-height: 44px`; `prefers-reduced-motion` disables the zone-flash pulse (chime/color/label still confirm the state without motion).
- **Pinch-zoom split by screen** — `setViewportZoomEnabled()` (`js/app.js`) disables zoom only while the live dashboard is visible, enabled on auth/settings for a low-vision user setting up the app. The iOS-rotation-bug workaround script in `index.html` had to be rewritten to read the *current* viewport content live rather than a page-load-time snapshot, or it would silently undo this toggle on every rotation.
- **Haptic feedback** (`navigator.vibrate()`) alongside the zone chime, pulse count scaling with valence the same way chime pitch does; no-ops harmlessly on iOS Safari (never implemented the API).
- A **color-blindness simulator check** (Chromium's `Emulation.setEmulatedVisionDeficiency`) confirmed protanopia/deuteranopia genuinely collapse green/yellow/red toward a similar hue — validating that the redundant text+number coding is load-bearing for colorblind users, not decorative.

The one remaining flagged item (`page-has-heading-one` — no `<h1>` on the live dashboard) is a deliberate scope decision, not a gap: the dashboard functions like an instrument cluster glanced at by a sighted person driving, not a document read by a screen-reader-primary user.

**Supabase access model** (see `supabase/migrations/`): the project was created with "Automatically expose new tables" turned **off**, so any *new* table needs an explicit `grant select, insert on public.<table> to authenticated;` or the API will reject all access to it regardless of RLS policies — this is a common silent-failure trap when adding tables. RLS policies scope both `insert` and `select` to `auth.uid() = user_id`, so each signed-in user can only write/read their own rows; nothing is granted to the `anon` role at all, so unauthenticated requests are rejected before RLS even runs. Only the developer (via the Supabase dashboard or a service-role key, which must never be added to client code) can see the full table across users. The anon key hardcoded in `js/supabaseClient.js` is safe to have committed — RLS is the actual access boundary, not key secrecy. `vehicle_fuel_economy` (added 2026-08-03, see the fuel-cost trip summary entry above) is the one exception to the per-user-row pattern described here: shared reference data every `authenticated` user can `select`, written only by the weekly refresh Action's service-role key.

**Privacy invariant to preserve in any future change**: no raw GPS coordinates ever get sent to Supabase or logged anywhere off-device — only derived scalar metrics. This is a standing project requirement (from the professor meeting that set this architecture), not just current scope; if a change would add a lat/lng field to any outgoing payload, that's a decision to raise explicitly, not make silently. **One explicit, discussed exception exists as of 2026-07-25**: the speed-limit lookup (see above) sends the driver's current lat/lng transiently to OpenStreetMap's Overpass API on each throttled query — never stored, never sent to Supabase, never logged to disk, and disclosed in the Privacy settings section. Any *further* third-party lookup would need the same explicit conversation, not a silent extension of this precedent.
