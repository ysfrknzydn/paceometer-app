## Medium — do these first

- [x] **Rate-limit the `transcribe-feedback` Edge Function** (2026-08-08) — before forwarding to Groq, the function now opens a Supabase client using the *caller's own* Authorization header (not the service role), so the existing `feedback: users select own` RLS policy scopes a `count` query to just their own rows with no extra filter needed. Past 10 submissions in the last hour, returns 429. Fails **open** on a count-query error (network blip) rather than blocking a legitimate submission over an unrelated hiccup. `js/ui/feedbackRecorder.js` now shows a specific "Too many feedback submissions — try again in a bit." message for a 429 (reading `error.context.status` off the real `FunctionsHttpError`, verified against the actual `@supabase/functions-js` source, not assumed) and hides the Retry button for that case specifically, since retrying immediately would just hit the same limit again. Covered by a new e2e test. **Needs deploying — see handoff below.**
- [x] **Validate file size before forwarding to Groq** (2026-08-08) — rejects `audioFile.size === 0` or `> 10MB` before the `fetch` to Groq. Verified live via `curl` against the function running locally (`deno run`, no Docker needed) with an actual 11MB file — rejected correctly, before ever reaching the rate-limit check or Groq. **Needs deploying — see handoff below.**

## Low — cheap, worth doing

- [x] **Add `CHECK` constraints to `trips`/`feedback` columns** (2026-08-08) — new migration, `NOT VALID` (enforces on every future write immediately; deliberately skips scanning the 51 existing live rows, so the migration itself can't fail if a historical row happens to violate a bound — this project's own math has always stayed within these generous ranges, but that's not something to bet a failed migration on). **Needs pushing — see handoff below.**
- [x] **Tighten the Edge Function's CORS origin** (2026-08-08) — changed from `"*"` to an explicit allow-list (the real GitHub Pages origin plus `localhost:8000`/`127.0.0.1:8000`, since this project is routinely tested locally against this exact real Edge Function, not a mock — a single production-only origin would have silently broken every local test run). Verified via `curl` with different `Origin` headers: an allowed origin gets echoed back, a random origin falls back to the production one (so the browser correctly blocks it client-side). **Needs deploying — see handoff below.**
- [x] **"Prevent use of leaked passwords" checked (2026-08-08) — not actually available, paywalled.** Confirmed in the dashboard: "Only available on Pro plan and above." Not a free toggle as assumed when this item was first written — not worth upgrading to Pro just for this. **Do not re-investigate this later thinking it was skipped** — it's genuinely inaccessible on the Free tier this project runs on.
- [x] **Password requirements strengthened (2026-08-08)** — dashboard's "Password requirements" dropdown changed from "Select an option" (no character-class rule) to **"Lowercase, uppercase letters, digits and symbols (recommended)"**, Supabase's own strongest offered option. Free, no paywall.
- [x] **Minimum password length raised from 6 to 8 (2026-08-08) — done both in the dashboard and in the app.** Matches Supabase's own "8 or more is recommended" note; you've confirmed the dashboard field is set and saved. **Real lockout bug caught and fixed while wiring up the client-side match**: `#password` is shared between sign-in and sign-up in `js/auth.js`; a static `minlength="8"` on it would have client-side-blocked *sign-in* for any account with a password shorter than 8 (including the standing test account), even though their real credentials are entirely valid server-side — `minlength` is meant for validating a *new* password being created, not for gatekeeping an existing one. Fixed by making `#password`'s `minLength` mode-dependent in `AuthController._setMode()`: 8 for sign-up (the real new floor), 6 for sign-in (every account ever created here has always required at least 6, Supabase's original floor, so 6 is always safe for checking an existing password). `#new-password` (the password-*reset* "set a new password" field, never used to check an old one) stays statically at 8 — no equivalent risk there. Covered by a new e2e test (`tests/e2e/specs/auth.spec.js`) asserting the attribute value changes correctly across mode switches. **Reassured live to the user**: an existing account's password is checked by hash comparison at sign-in, never re-validated against a new policy — an existing shorter/simpler password keeps working indefinitely; the new rules only apply the next time a password is *created* (signup or a future change/reset).
- [x] **Password requirements hint added to the UI (2026-08-08)** — raised as a follow-up ("does the app warn users about the requirements?") after the dashboard changes above: the character-class rule is enforced server-side only (no client-side `pattern` check), so previously a driver only found out they were missing a symbol/digit *after* submitting and getting a Supabase rejection back. New `#password-requirements-hint` (sign-up only, toggled in `AuthController._setMode()` — hidden at sign-in, since an existing password was never checked against this rule and never will be) and a static equivalent under `#new-password` (always relevant there, no mode toggle needed — that field only ever creates a brand-new password). Verified with real screenshots in both themes across all three states (hidden at sign-in, visible at sign-up, visible at set-new-password) and a new e2e assertion.
- [ ] **"Require current password when updating" — investigated, deliberately left off.** Would close a real gap (a hijacked/stale session alone, with no password knowledge, can currently change the account password) — but Supabase's own docs don't clearly state whether this exemption covers a `PASSWORD_RECOVERY` session established via the forgot-password email link (checked their password-security guide directly; it documents the *separate* session-recency "Secure password change" setting's recovery-session exemption, but is silent on this one). This app's existing password-reset flow calls `updateUser({ password })` without a current password by design (the whole premise of "forgot password" is not remembering the old one) — enabling this without confirmed exemption behavior risks silently breaking the self-serve reset flow already built and verified end-to-end with a real email round-trip (2026-08-06). If this is ever revisited: turn it on, then immediately re-run a real password-reset-via-email test before trusting it.
- [x] **Auth Redirect URLs allow-list verified tight (2026-08-08).** Checked live in the dashboard: **Site URL** is `https://ysfrknzydn.github.io/paceometer-app/` (the real deployed app, not localhost — the earlier 2026-08-06 fix held). **Redirect URLs** has exactly one entry, `https://ysfrknzydn.github.io/paceometer-app/**` — the `**` wildcard only matches paths *under that same domain*, it can't redirect anywhere else. `js/auth.js`'s dynamically-built `redirectTo` (`window.location.origin`) is safe given this allow-list.
- [x] **CAPTCHA — deliberately left off (2026-08-08), logged for later reconsideration.** Signup is already gated behind the invite-allowlist Auth Hook (blocks anyone not invited, bot or not), so CAPTCHA would mostly add friction for real invited people without stopping much it's actually good at, at this app's current invite-only scale. **Revisit if signup is ever opened beyond invite-only** — that's the point at which CAPTCHA starts pulling real weight.

## Second-pass findings (2026-08-08, later the same day)

- [x] **Validate the uploaded audio file's content-type, not just presence/size** — `transcribe-feedback` checked `audioFile instanceof File`, `size === 0`, and `size > MAX_AUDIO_BYTES`, but never checked `audioFile.type` before forwarding it to Groq. Low severity (the endpoint is already authenticated, rate-limited, and never persists the file — Groq validates it independently too), but a real gap against defense-in-depth. Fixed with an `ALLOWED_AUDIO_TYPES` allow-list (`audio/webm`, `audio/ogg`, `audio/mp4`, `audio/wav`, `audio/mpeg` — covers what `MediaRecorder`'s default actually produces per browser; `feedbackRecorder.js` never forces a `mimeType`), matched against `audioFile.type` with any codec suffix stripped (`Blob.type` can read `"audio/webm;codecs=opus"`). **Needs deploying — see handoff below.**
- [x] **Stop surfacing raw Supabase/PostgREST error text on a failed trip save** — `js/app.js`'s `endTrip()` showed `` `Save failed: ${error.message}` `` verbatim, which can include column/constraint names. Low sensitivity (the schema's already public in this repo) but an unfiltered passthrough worth closing on principle, especially since it was flagged as an open item in the Informational section below rather than actually fixed. Now shows a generic "Save failed — try again." except for the one case that's genuinely actionable to the driver ("Not signed in").
- [x] **Add `CHECK` constraints to the *text* columns the first `CHECK`-constraints pass missed** — the 2026-08-08 migration below (`20260808045856`) bounded every numeric column on `trips`/`feedback` but left `vehicle_label`, `user_agent`, and `zone_state` completely unbounded — a signed-in user could insert an arbitrarily long string into either, or a `zone_state` value outside the app's own `"green" | "yellow" | "red" | "limit" | null` vocabulary. Same reasoning as the original pass: RLS already blocks touching anyone else's data, so this is a cheap sanity bound on top of that, not a response to a proven exploit. New migration, `supabase/migrations/20260808151107_add_text_check_constraints_to_trips_and_feedback.sql`, `NOT VALID` for the same reason as the original pass (enforces on future writes, doesn't scan/risk failing against live rows). **Needs pushing — see handoff below.**

**Investigated, deliberately left as-is (not a gap):**
- **Session token in `localStorage`, not an httpOnly cookie.** Raised again this pass since it's the one remaining ⚠️ item with no code fix. Confirmed the reasoning still holds: an httpOnly cookie can only be set by a server responding to the login request, and this app has none — it's static HTML/CSS/JS on GitHub Pages talking directly to Supabase's REST/Auth API, with no request-handling layer anywhere that could emit a `Set-Cookie` header. Supabase's cookie-based session adapter (`@supabase/ssr`) exists but is built for frameworks with a server component (Next.js, SvelteKit) to proxy the cookie through — adopting it here means adding a real backend, which is an architecture decision for the project owner to make, not something a security-audit pass should slip in as a "fix." Left alone; mitigated by the same verified-clean XSS surface noted below (no known vector currently exploits this).

## What's already confirmed solid (don't accidentally break these)

- RLS is correct and comprehensive on every per-user table (`trips`, `feedback`) — `auth.uid() = user_id` on every policy, `WITH CHECK` on every insert/update, never `user_metadata`-based identity.
- `invite_allowlist`'s RLS-*disabled* design is deliberate and actually secure (verified the `REVOKE ALL FROM authenticated, anon, public` is comprehensive) — don't "fix" this by re-enabling RLS without also adding policies, or signup breaks the same way it did on 2026-08-05.
- Zero `SECURITY DEFINER` functions anywhere in the schema.
- Service-role key never appears client-side — only ever referenced via `os.environ[...]` (Python) and `${{ secrets.* }}` (GitHub Actions).
- No hardcoded secrets anywhere — the only JWT-looking string in the codebase is the public `anon` key (decoded and confirmed `"role":"anon"` during the audit, not just assumed).
- Every write derives identity from `getUser()` (server-verified), never a client-supplied `user_id` — backed up independently by RLS even if a client lied.
- The Edge Function fails closed (500, not a silent proceed) if `GROQ_API_KEY` is missing — verified live.
